# Audio Event Detection 开发指南

> 版本：1.2  
> 更新日期：2026-06-23  
> 开发策略：模拟器优先，固定测试向量优先，真实硬件最终验收

openvela Sim 音频能力和宿主 ALSA 配置可参考
[Sim 环境音频功能开发指南](../../../../docs/zh-cn/quickstart/emulator/sim_audio_guide.md)。

当前真实硬件主路径为 ESP32-S3 DevKit + INMP441；ESP32-S3-BOX/BOX-3
移植材料已归档到 `../../../archive/esp32s3-box-3/`，仅作为历史问题回溯。

## 1. 文档目标

本文档说明如何在 openvela 中开发和验证 `audio_event`，重点覆盖：

- 使用 NuttX 原生 Sim 验证 TFLite Micro 模型。
- 使用 HostFS 输入固定 PCM 和黄金特征。
- 实现与训练端一致的 `49x40` log-mel。
- 通过宿主机 ALSA 麦克风验证连续采集。
- 将模拟器实现迁移到真实开发板。

开发顺序遵循以下原则：

```text
黄金 INT8 特征
  -> TFLite Micro 推理
  -> 固定 PCM + log-mel
  -> 连续文件输入
  -> ALSA 麦克风
  -> 真实开发板
```

每一步只增加一个变量。模型、DSP、音频驱动出现问题时，可以快速定位到具体层。

### 1.1 结论与边界

本项目可以使用 openvela Sim 完成大部分功能开发和回归测试，但不能只凭 Sim 宣布端侧交付完成。

| 环境 | 主要用途 | 可以验证 | 不能替代 |
|---|---|---|---|
| NuttX 原生 Sim + 文件 | 第一开发环境 | TFLM、log-mel、滑窗、阈值、异常路径 | 麦克风驱动、MCU 性能和功耗 |
| NuttX 原生 Sim + ALSA | 连续音频联调 | NuttX Audio API、宿主麦克风、持续运行 | 目标 codec、I2S/PDM 和现场声学表现 |
| Goldfish/QEMU | 系统镜像验证 | NSH、应用注册、HostFS、AP 镜像集成 | MCU 指令集性能和真实音频硬件 |
| 真实开发板 | 最终验收 | 完整闭环、延迟、RAM、Flash、功耗、距离与噪声 | - |

推荐主线是“原生 Sim 文件模式 -> 原生 Sim ALSA -> 真实开发板”。Goldfish/QEMU 是可选的系统集成验证，不应阻塞算法开发。

### 1.2 最短开发路径

| 阶段 | 输入 | 完成标志 |
|---|---|---|
| S0 | 黄金 `int8[1960]` | TFLM 输出与桌面 TFLite 一致 |
| S1 | 1 秒固定 PCM | C/C++ log-mel 与训练端处于容差内 |
| S2 | 连续 PCM 文件 | 滑窗、连续确认、冷却和事件合并正确 |
| S3 | `/dev/audio/pcm0c` | 宿主麦克风可连续推理 30 分钟 |
| H0 | 真实麦克风 | 两类事件闭环和板端性能通过验收 |

当前代码已经完成 Native Sim 文件输入、ALSA 采集、log-mel、TFLite Micro
推理和告警闭环。当前阻塞点是 Python/C 特征黄金向量尚未对齐，并且真实安静
环境长期误判为 `knock`。在完成数值对齐和真实数据校准前，不能把现有模型作为
硬件部署基线。

## 4. 测试架构

### 4.1 双输入模式

建议把音频来源抽象为统一接口：

```c
struct audio_source_s;

int audio_source_open(struct audio_source_s *source,
                      const struct audio_source_config_s *config);
int audio_source_read(struct audio_source_s *source,
                      int16_t *samples, size_t sample_count);
void audio_source_close(struct audio_source_s *source);
```

实现两种 source：

1. `file`：从 HostFS 读取固定 PCM，用于回归测试。
2. `device`：从 `/dev/audio/pcm0c` 或目标板录音设备读取。

建议的命令行：

```text
audio_event --file /host/knock.pcm --once
audio_event --file /host/background.pcm --repeat 20
audio_event --device /dev/audio/pcm0c
```

上述接口已经实现。文件模式用于数值回归，设备模式用于 Sim ALSA 和真实板录音。

在真实开发板上不传参数时，默认使用 Kconfig 配置的设备路径。

### 4.2 三个测试入口

为了隔离问题，建议支持三个入口：

| 入口 | 输入 | 验证范围 |
|---|---|---|
| 模型测试 | `int8[1960]` | resolver、Arena、Invoke、类别映射 |
| DSP 测试 | 1 秒 PCM | log-mel、量化、模型输出 |
| 应用测试 | 连续 PCM/麦克风 | 环形缓冲、阈值、去抖、告警 |

生产构建可以关闭测试入口，但不要删除测试代码和黄金数据说明。

## 5. 开发环境

### 5.1 推荐模拟器

第一阶段使用 NuttX 原生 Sim：

```text
nuttx/boards/sim/sim/sim/configs/tflm/defconfig
```

这个配置已经启用：

- C++ 和 libc++。
- FlatBuffers。
- Gemmlowp。
- KISS FFT。
- Ruy。
- TFLite Micro。
- HostFS。

它直接在 Linux 宿主机上运行，构建和调试速度快，适合验证算法与内存问题。

Goldfish/QEMU 可在后续验证 openvela AP 镜像和 NSH 集成，但不作为第一阶段音频算法测试环境。

这里的“原生 Sim”是编译为 Linux 宿主进程的 NuttX `sim` 架构；它与通过 `emulator.sh` 启动的 Goldfish/QEMU 不是同一个运行环境。

### 5.2 文件输入阶段配置

以 `sim:tflm` 为基础增加：

```text
CONFIG_AUDIO=y
# CONFIG_SIM_SOUND is not set
CONFIG_EXAMPLES_AUDIO_EVENT=y
```

文件模式虽然不访问麦克风，但当前应用 Kconfig 依赖 `AUDIO`，因此仍需启用 `CONFIG_AUDIO`。关闭 `SIM_SOUND` 可以避免第一阶段依赖宿主机 ALSA。

### 5.3 ALSA 麦克风阶段配置

实时录音阶段再启用：

```text
CONFIG_AUDIO=y
CONFIG_SIM_SOUND=y
CONFIG_SIM_SOUND_ALSA=y
CONFIG_EXAMPLES_AUDIO_EVENT=y
```

Sim 音频驱动会注册：

```text
/dev/audio/pcm0p    playback
/dev/audio/pcm0c    capture
```

Linux 宿主机需要 ALSA 开发头文件。当前 Sim ALSA 配置还依赖 MAD 和 LAME；如果使用 32 位 `SIM_M32` 配置，宿主依赖也必须提供对应的 32 位开发包。建议从 64 位 `sim:tflm` 配置派生，减少多架构依赖。

进入 ALSA 阶段前可以检查宿主依赖：

```bash
test -f /usr/include/alsa/asoundlib.h
test -f /usr/include/mad.h
test -f /usr/include/lame/lame.h
```

缺少头文件时，先安装当前 Linux 发行版对应的开发包。文件输入阶段不需要这些依赖。

## 6. 配置与构建

### 6.1 重新生成 Examples Kconfig

`apps/examples/Kconfig` 是生成文件。新增应用后如果 menuconfig 中看不到 `Audio event detection demo`，在仓库根目录执行：

```bash
cd apps/examples
../tools/mkkconfig.sh -m "Examples"
cd ../..
```

CMake 配置会调用 Kconfig 生成逻辑；上面的命令主要用于 legacy Make 配置或生成文件尚未刷新的情况。

### 6.2 配置原生 Sim

> 本节命令用于 Native Sim 开发配置。当前模型推理、文件 source 和 ALSA 设备
> source 均已接入；构建后可直接执行模型冒烟、固定文件和实时麦克风测试。

从仓库根目录执行：

```bash
cd nuttx
tools/configure.sh -l sim:tflm
make menuconfig
```

在 menuconfig 中启用本节要求的 `AUDIO` 和 `EXAMPLES_AUDIO_EVENT`。文件输入阶段关闭 `SIM_SOUND`。

构建：

```bash
make -j$(nproc)
```

运行：

```bash
./nuttx
```

也可以从仓库根目录使用：

```bash
./build.sh sim:tflm -j$(nproc)
```

使用 `build.sh` 前仍需确保目标配置已经包含 `audio_event` 所需选项。

### 6.3 挂载 HostFS

准备宿主测试目录，例如：

```text
/home/user/audio_event_test/
├── knock.pcm
├── cough.pcm
├── background.pcm
├── silence.pcm
└── golden/
```

在 NuttX NSH 中挂载：

```bash
mkdir /host
mount -t hostfs -o fs=/home/user/audio_event_test /host
ls /host
```

HostFS 用于测试数据交换，不要求 Sim 内部提供 WAV 解码器。

第一阶段推荐使用原始 PCM：

- signed 16-bit little-endian。
- 16000 Hz。
- 单声道。
- 每 1 秒恰好 32000 bytes。

WAV 输入需要额外解析 RIFF header、采样率、位宽和声道，不应把 header 当作 PCM 样本。

## 7. 分阶段实现

### 7.1 阶段 1：TFLite Micro 模型冒烟测试

目标：不依赖音频和 DSP，证明模型可以在 Sim 上运行。

修改内容：

1. 将 `model/event_classifier.c` 改为 `.cc`。
2. 保留 `event_classifier.h` 的 `extern "C"` 接口。
3. 将 `model/model.cc` 加入 CMake 和 Make 源文件。
4. 注册模型实际需要的 9 类算子。
5. 静态分配 64-96 KB Tensor Arena。
6. 调用 `AllocateTensors()` 并打印实际 Arena 使用量。
7. 校验输入输出 tensor 的类型、shape、scale 和 zero point。
8. 填充一份黄金 `int8[1960]` 输入并调用 `Invoke()`。

验收输出示例：

```text
[model] schema=3
[model] input=int8 [1,1960] scale=0.101961 zp=-128
[model] output=int8 [1,4] scale=0.00390625 zp=-128
[model] arena_used=xxxxx
[model] result=knock probability=0.xxx
```

注意：仓库自带 `tflm_tool` 的 resolver 不包含当前模型的全部算子，也没有业务输入注入接口，不能原样用于本模型验收。

### 7.2 阶段 2：文件音频源

目标：从 HostFS 稳定读取 1 秒 PCM。

实现要求：

- 打开指定文件并检查大小。
- 循环处理短读，直到获得 16000 个样本或到达 EOF。
- 明确处理尾部不足 1 秒：返回错误或补零，测试中保持固定策略。
- `--once` 模式只推理一次并退出。
- `--repeat N` 用于检查内存和输出稳定性。
- 文件源不访问 `/dev/audio/*`。

测试：

```text
knock.pcm       -> 应预测 knock
cough.pcm       -> 应预测 cough
background.pcm  -> 不告警
silence.pcm     -> 不告警
short.pcm       -> 明确报错或按规则补零
missing.pcm     -> 返回可读错误，不崩溃
```

### 7.3 阶段 3：log-mel 前处理

目标：固件端生成与训练端一致的 1960 个特征。

流水线：

```text
PCM[16000]
  -> 49 个分析帧
  -> 窗函数
  -> FFT/功率谱
  -> 40 路 Mel filterbank
  -> log
  -> feature[49][40]
  -> flatten[1960]
```

实现前必须从训练端补齐：

- PCM 缩放和预处理。
- 窗函数。
- FFT 点数。
- 功率谱定义。
- Mel 频率上下限和公式。
- log 底数和 epsilon。
- 归一化方式。
- 展平顺序。

不要仅凭 `tensorflow_log_mel` 猜测参数。

黄金测试至少比较：

| 指标 | 说明 |
|---|---|
| shape | 必须为 `[49,40]` |
| 最大绝对误差 | 定位局部实现差异 |
| 平均绝对误差 | 判断整体偏移 |
| INT8 不同元素比例 | 判断量化后的实际影响 |
| 最终类别 | Python、桌面 TFLite、TFLM 必须一致 |

### 7.4 阶段 4：事件判定

固定类别表：

```text
0 knock
1 cough
2 background
3 silence
```

初始判定策略：

```text
knock >= 0.75 且连续 2 次 -> 告警
cough >= 0.75 且连续 2 次 -> 告警
background / silence       -> 清除连续命中计数
告警后冷却 1-2 秒
```

禁止使用 `event_id > 0` 判断目标事件，因为 `knock` 的 ID 为 0，而 `background`、`silence` 的 ID 大于 0。

日志应包含：

```text
timestamp, window_id, class_id, class_name, probability,
threshold, consecutive_hits, alert_fired
```

### 7.5 阶段 5：连续文件窗口

目标：模拟实时流而不引入麦克风驱动。

实现一个至少 16000 samples 的环形缓冲区：

- 按固定块大小读取 PCM。
- 缓冲满 1 秒后开始推理。
- 初始推理 hop 为 250 ms，即 4000 samples。
- 每次推理仍读取最近完整 1 秒。
- EOF 后退出并输出事件汇总。

该阶段可以完整验证滑窗、连续确认、冷却和事件合并逻辑。

### 7.6 阶段 6：ALSA 麦克风

目标：通过宿主机麦克风模拟真实持续采集。

重要：NuttX Audio 不是普通字符设备的简单 `read()` 接口。设备源需要完成：

1. 打开 `/dev/audio/pcm0c`。
2. 查询并配置输入能力。
3. 配置 16 kHz、16-bit、单声道 PCM。
4. reserve session。
5. 分配并 enqueue audio buffers。
6. start capture。
7. 通过消息队列接收完成缓冲区并重新 enqueue。
8. stop、release 并释放资源。

可以先用 `nxrecorder` 验证宿主 ALSA 和 Sim 驱动：

```text
nxrecorder
device pcm0c
recordraw /host/capture.pcm 1 16 16000
```

只有 `nxrecorder` 能稳定生成正确 PCM 后，才调试应用设备源。

### 7.7 阶段 7：Goldfish/QEMU 系统集成（可选）

目标：验证应用在 openvela AP 镜像中的注册、启动、文件访问和异常处理。

建议只复用已经在原生 Sim 通过的文件输入测试：

1. 在 Goldfish/QEMU 配置中启用 TFLite Micro 依赖和 `EXAMPLES_AUDIO_EVENT`。
2. 通过模拟器 HostFS 或 ADB 将黄金 PCM 放入可访问目录。
3. 运行一次性文件推理并核对日志。
4. 检查应用重复启动、退出和错误文件路径。

Goldfish/QEMU 的通过结果不能替代真实板上的音频采集、性能和功耗数据。

## 10. 调试指南

### `AllocateTensors()` 失败

检查顺序：

1. resolver 是否包含全部算子。
2. Tensor Arena 是否足够且对齐。
3. 模型数组是否完整。
4. schema 版本是否匹配。
5. 开启 `CONFIG_TFLITEMICRO_DEBUG` 查看详细错误。

### `Invoke()` 报找不到算子

不要根据 Keras 层名猜 resolver。以 `.tflite` FlatBuffer 的 operator code 为准。

### 所有音频都预测同一类别

依次比较：

1. 原始 PCM 是否为 16 kHz 单声道。
2. PCM 是否错误读取了 WAV header。
3. log-mel 参数和展平顺序。
4. 输入量化 scale、zero point 和 clamp。
5. 类别顺序。

### Sim 没有 `/dev/audio/pcm0c`

检查：

- `CONFIG_AUDIO=y`。
- `CONFIG_SIM_SOUND=y`。
- `CONFIG_SIM_SOUND_ALSA=y`。
- 宿主 ALSA 开发依赖是否存在。
- 先运行 `nxrecorder` 隔离驱动问题。

### menuconfig 找不到 audio_event

重新生成 `apps/examples/Kconfig`，然后重新执行 configure。不要手工向生成文件追加固定路径。

## 11. 性能记录

模拟器阶段记录功能数据：

- Tensor Arena 实际使用量。
- 单次 DSP、Invoke 和完整窗口耗时。
- 连续运行次数。
- 事件判定日志。
- Python、桌面 TFLite、TFLM 的输出差异。

模拟器耗时不能作为 MCU 性能指标。目标板必须重新测量：

- DSP 耗时。
- 推理耗时。
- 端到端告警延迟。
- 峰值 RAM 和栈。
- Flash 增量。
- 功耗。
- 不同距离和噪声下的误报、漏报。

建议报告明确标注数据来源：

```text
[SIM-FILE] 功能回归和数值一致性
[SIM-ALSA] 连续采集和稳定性
[QEMU]     系统镜像集成
[BOARD]    最终性能和现场效果
```

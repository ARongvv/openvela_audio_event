## 1. 项目概述

### 1.1 定位与目标

`audio_event` 是运行在 openvela (NuttX) RTOS 上的**离线音频事件检测系统**。它实现了从麦克风采集到本地告警的完整闭环，无需云端、无需网络。

```text
麦克风 → 1秒音频缓存 → log-mel 特征提取 → TFLite Micro 推理 → 事件判定与去抖 → 串口/LED/蜂鸣器告警
```

**识别目标**：`knock`（敲门声）和 `cough`（咳嗽声），`background` 和 `silence` 为拒识类别。

### 1.2 架构分层

## 2. 代码逻辑深度分析

### 2.1 主循环：滑动窗口驱动的推理流水线

**文件**：[audio_event_main.c](../main/audio_event_main.c)（389 行）

这是整个应用的**心跳**。核心逻辑围绕一个环形缓冲区和滑动窗口展开。

**数据结构**：

```c
// 全部全局静态分配 —— 嵌入式标准做法
static int16_t g_audio_ring[AUDIO_EVENT_CLIP_SAMPLES];      // 32000 bytes = 1秒
static int16_t g_audio_window[AUDIO_EVENT_CLIP_SAMPLES];    // 32000 bytes
static int16_t g_audio_block[AUDIO_IO_BLOCK_SAMPLES];       // 1024 bytes = 512 样本
static float    g_features[AUDIO_EVENT_FEATURE_SIZE];       // 7840 bytes = 1960 floats
static float    g_probabilities[AUDIO_EVENT_CLASS_COUNT];   // 16 bytes = 4 floats
```

**主循环算法流程**：

```text
初始化：
  ├── parse_options()           CLI 参数解析（--file/--device/--once/--repeat/--model-smoke）
  ├── event_classifier_init()   加载模型、注册算子、分配 Tensor Arena
  ├── feature_extract_init()    预计算 Hann 窗、Mel 映射表
  ├── event_detector_init()     初始化连续命中/冷却状态
  ├── event_alert_init()        初始化告警通道
  └── audio_source_open()       打开文件或设备

主循环 (for(;;)):
  │
  ├── 从音频源读取 512 样本块 → g_audio_block
  ├── ring_append(write_pos, block, count)     ← 写入环形缓冲
  ├── samples_until_inference -= count
  │
  └── if samples_until_inference == 0:         ← 到达 hop 边界
       ├── ring_copy_window(write_pos)          ← 取出最近 1 秒
       ├── feature_extract_compute()             ← log-mel 特征
       ├── event_classifier_predict()            ← TFLM 推理
       ├── print_probabilities()                 ← 日志输出
       ├── event_detector_update()               ← 去抖判定
       ├── if detection.fired:
       │     event_alert_fire()                  ← 触发告警
       │
       ├── if --once: break                     ← 单次推理退出
       └── samples_until_inference = hop_samples ← 设置下一次触发距离
```

**为什么是 512 样本块？**

每次从音频源读取 512 个样本（约 32ms），这个值并非随意选择：
1. 与音频驱动的内部缓冲区大小对齐（`CONFIG_AUDIO_BUFFER_NUMBYTES` 通常为 8192 bytes = 4096 样本，512 是其整数约数）
2. 足够小以保证主循环响应及时（不会在 read 上阻塞太久）
3. 与 FFT 的 512 点变换同值——虽然这纯粹是巧合（FFT 用 512 是因为它是大于 480 的最小 2^n）

### 2.2 环形缓冲区：零拷贝窗口提取

**文件**：[audio_event_main.c:165-188](../main/audio_event_main.c#L165-L188)

**设计动机**：滑动窗口推理中相邻窗口有大量重叠。例如 hop=250ms (4000 样本) 时，相邻两次推理共享 12000 个样本。如果每次重新采集 1 秒音频，超低效。

**写入（生产者）**：

```c
static void ring_append(size_t *write_position, const int16_t *samples,
                        size_t sample_count) {
    for (i = 0; i < sample_count; i++) {
        g_audio_ring[*write_position] = samples[i];
        *write_position = (*write_position + 1) % AUDIO_EVENT_CLIP_SAMPLES;
        //    ^── 取模回绕，实现环形
    }
}
```

**窗口提取（消费者）**—— 两段拷贝：

```c
static void ring_copy_window(size_t write_position) {
    size_t tail = AUDIO_EVENT_CLIP_SAMPLES - write_position;

    // 复制 "尾部"：[write_pos ... 数组末尾]
    memcpy(g_audio_window, &g_audio_ring[write_position],
           tail * sizeof(int16_t));

    // 复制 "头部"：[0 ... write_pos-1]  —— 仅在 write_pos > 0 时需要
    if (write_position > 0) {
        memcpy(&g_audio_window[tail], g_audio_ring,
               write_position * sizeof(int16_t));
    }
}
```

**可视化**（write_position = 12000 时的窗口提取）：

```text
g_audio_ring:  [====== write_pos=12000 ======|========== tail=4000 =========]
                 ←── 头部(较新数据) ──→        ←── 尾部(最旧数据) ──→
                                              ↓ memcpy #1
                                              [tail 4000 样本]
                ↑ memcpy #2 (如果 write_pos > 0)
                [head 12000 样本]

g_audio_window: [tail 4000 样本][head 12000 样本] = 连续的最近 1 秒
```

**时间复杂度**：O(N) —— 总是复制全部 16000 个样本。没有使用双缓冲或零拷贝技巧，适合嵌入式场景的数据量级（32000 bytes，MCU 上 < 1ms）。

### 2.3 特征提取：49×40 log-mel 前端

**文件**：[feature_extract.c](../dsp/feature_extract.c)（171 行）

这是整个项目中**计算量最大**的模块，必须在数值上与训练端（Python TensorFlow `log_mel`）逐元素一致。

**完整流水线**：

```text
PCM[16000] (int16, 时域波形)
  │
  ├─ 分 49 帧，每帧 480 样本 (30ms)，帧移 320 样本 (20ms)
  │   frame_offset = frame × 320
  │
  ├─ 每帧处理：
  │   1. int16→float: audio = sample / 32768.0f
  │   2. Hann 窗:    windowed = audio × hann[i]
  │   3. 补零到 512: 后 32 个点填 0
  │   4. 512 点实数 FFT (kiss_fftr)
  │   5. 幅度计算:    magnitude = sqrt(real² + imag²)
  │   6. Mel 滤波器组: 40 路三角形加权累加
  │      - 257 个 FFT bin → 40 个 Mel 通道
  │      - bin[0] (DC) 显式跳过 ← 与 TensorFlow 一致
  │   7. 对数变换:     log(mel_energy + 1e-6)
  │   8. 归一化:      (log_val + 12.0) × 1.625
  │   9. 截断:        clamp(0.0, 26.0)
  │
  └─ 展平: features[49×40] = features[1960] (float)
```

**关键常量与训练端对齐**：

```c
#define MEL_LOWER_HZ    125.0f     // Mel 频带下限
#define MEL_UPPER_HZ   7500.0f     // Mel 频带上限（16kHz 采样率 Nyquist=8kHz）
#define LOG_EPSILON       1.0e-6f  // 防止 log(0) = -inf
#define FEATURE_OFFSET   12.0f     // 偏移，与 TensorFlow 归一化对齐
#define FEATURE_SCALE     1.625f   // 缩放，确保值域 [0,26] 与 INT8 量化匹配
#define FEATURE_MIN       0.0f
#define FEATURE_MAX      26.0f     // 26 / 0.101961 ≈ 255，恰好覆盖 INT8 256 级
```

**预计算策略**（`feature_extract_init()`）：

```c
// 1. Hann 窗预计算 → 避免每帧 480 次 cosf()
for (i = 0; i < 480; i++)
    g_hann[i] = 0.5f - 0.5f * cosf(2π × i / 480);

// 2. FFT bin → Mel 映射预计算 → 避免每帧 257 次 hertz_to_mel()
for (i = 0; i <= 256; i++)
    g_bin_mel[i] = hertz_to_mel(bin_to_hertz(i));

// 3. Mel 频带边缘预计算 → 40 个三角形滤波器的起/中/终点
//    g_band_edge_mel[42] —— 在 [125, 7500] Hz 上均匀分布
```

**为什么 DC bin 要跳过？**

```c
for (bin = 1; bin <= 256; bin++) {  // ← 从 1 开始，不是 0
    ...
}
```

TensorFlow 的 `tf.signal.linear_to_mel_weight_matrix` 显式将 DC 行设为零。CF 代码必须保持一致，否则第一个 Mel 通道会有系统性偏差。

**Hertz → Mel 公式**：

```c
static float hertz_to_mel(float hertz) {
    return 1127.0f * logf(1.0f + hertz / 700.0f);
}
```

这是标准公式（O'Shaughnessy, 1987），必须与 TensorFlow 使用的完全一致。

**三角形滤波器实现**：

```c
for (bin = 1; bin <= 256; bin++) {
    float mel = g_bin_mel[bin];
    if (mel <= lower || mel >= upper) continue;

    // 三角形权重：在 [lower, center] 上升，[center, upper] 下降
    if (mel <= center)
        weight = (mel - lower) / (center - lower);
    else
        weight = (upper - mel) / (upper - center);

    float magnitude = sqrtf(real² + imag²);
    mel_energy += magnitude * weight;  // 加权幅度（非能量） —— 与 TF 一致
}
```

### 2.4 TFLite Micro 推理封装

**文件**：[event_classifier.cc](../model/event_classifier.cc)（208 行）

虽然项目整体是 C 语言，但 TFLite Micro API 是 C++，因此这个文件是 `.cc` 扩展名，通过 `extern "C"` 向外暴露 C 接口。

**初始化流程**：

```text
event_classifier_init()
  ├─ 1. GetModel(g_audio_event_model)      ← 解析 FlatBuffer
  ├─ 2. 校验 schema 版本 (TFLITE_SCHEMA_VERSION)
  ├─ 3. OpResolver 注册 9 类算子（仅注册一次，static 变量记录状态）
  │      Shape, StridedSlice, Pack, Reshape,
  │      Conv2D, DepthwiseConv2D, Mean,
  │      FullyConnected, Softmax
  ├─ 4. 创建 MicroInterpreter(model, resolver, arena, arena_size)
  ├─ 5. AllocateTensors()                  ← 一次性内存规划
  ├─ 6. 校验输入张量: int8 [1, 1960]       ← 验证模型契约
  ├─ 7. 校验输出张量: int8 [1, 4]
  └─ 8. 打印模型信息（scale/zp/arena_used）
```

**INT8 量化 —— 前向路径**（float → int8）：

```c
// event_classifier_predict() — 核心量化代码
for (size_t i = 0; i < 1960; i++) {
    // 步骤 1: 缩放 → 取整
    long value = std::lround(features[i] / g_input->params.scale)
                 + g_input->params.zero_point;
    // 步骤 2: clamp 到 int8 范围
    if (value < -128) value = -128;
    else if (value > 127) value = 127;
    // 步骤 3: 写入模型输入
    g_input->data.int8[i] = static_cast<int8_t>(value);
}
// 步骤 4: 执行推理
g_interpreter->Invoke();
```

**INT8 量化 —— 反向路径**（int8 → float）：

```c
// read_output()
for (size_t i = 0; i < 4; i++) {
    probabilities[i] =
        (static_cast<int>(g_output->data.int8[i]) - g_output->params.zero_point)
        * g_output->params.scale;
}
```

**量化参数从模型自动读取**（非硬编码）：

```c
g_input->params.scale       // 0.101961  ← 来自 .tflite 文件
g_input->params.zero_point  // -128      ← 来自 .tflite 文件
g_output->params.scale      // 0.00390625
g_output->params.zero_point // -128
```

**为什么用 `std::lround` 而非简单的 `(int)(x + 0.5)`？**

- `lround` 对负数正确处理（`lround(-0.5) = -1`，而 `(int)(-0.5 + 0.5) = 0`）
- 与 TensorFlow Lite 训练端量化逻辑一致
- 符合 IEEE 754 就近舍入偶数（round-half-to-even）规则

**Resolver 只注册一次**（优化模式）：

```c
static tflite::MicroMutableOpResolver<9> resolver;
static bool resolver_initialized;

if (!resolver_initialized) {
    resolver.AddShape();          // 每次 init 注册，第二次 init 跳过
    ...
    resolver_initialized = true;
}
```

### 2.5 事件判定与去抖算法

**文件**：[event_detector.c](../detector/event_detector.c)（84 行）

这是"嵌入式去抖（Debounce）"模式在 AI 推理场景的经典应用。

**状态机**：

```text
全局状态:
  g_candidate        = -1    ← 当前候选事件类别
  g_hits             = 0     ← 连续命中计数
  g_cooldown_until_ms = 0    ← 冷却期截止时间

每 250ms 收到概率向量 [knock, cough, background, silence]:

  if 在冷却期 OR 最佳类别是拒识类 OR 概率 < 阈值:
    g_candidate = -1; g_hits = 0; return     ← 重置

  if 最佳类别 == g_candidate:
    g_hits++                                  ← 连续命中
  else:
    g_candidate = best; g_hits = 1            ← 切换候选

  if g_hits >= CONSECUTIVE_HITS (默认 2):
    detection->fired = true                   ← 触发！
    g_cooldown_until_ms = now + COOLDOWN_MS   ← 进入冷却
    g_candidate = -1; g_hits = 0              ← 重置
```

**参数配置（通过 Kconfig 可调）**：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `KNOCK_THRESHOLD` | 750‰ (0.75) | 敲门概率阈值 |
| `COUGH_THRESHOLD` | 750‰ (0.75) | 咳嗽概率阈值 |
| `CONSECUTIVE_HITS` | 2 | 需连续命中次数 |
| `COOLDOWN_MS` | 1500ms | 两次告警最小间隔 |

**为什么用千分比（permille）而非浮点数？**

Kconfig 不原生支持浮点值。`int 750` 在代码中除以 1000.0f 转为 `0.75f`。这是嵌入式配置体系的常见妥协。

**为什么同类连续命中后才能告警？**

单次推理可能产生瞬态误检（模型输出波动）。连续 2 次命中（间隔 250ms）意味着持续 250ms 的置信度——显著降低误报率。

**为什么冷却期重要？**

持续发生的音频事件（如连续的敲门声），每 250ms 都会触发推理。没有冷却期会产生告警风暴——同一事件重复告警数十次。

### 2.6 NuttX 异步音频 API 封装

**文件**：[audio_capture.c](../audio/audio_capture.c)（347 行）

NuttX Audio 子系统使用的是**异步 + 消息队列**模型，而应用层需要**同步阻塞**的 `read()` 语义。`audio_capture.c` 的核心价值就是封装这一层转换。

**异步模型原理**：

```text
传统的同步设备：            NuttX 异步音频设备：
  read() → 阻塞等待          ioctl(ENQUEUEBUFFER) → 交出空缓冲
  → 数据返回                    ↓ 驱动异步填充
                            消息队列通知 ← 驱动写满
                            ioctl(DEQUEUE) → 取回满缓冲
                            → 处理数据
                            → ioctl(ENQUEUEBUFFER) → 交回空缓冲
```

**完整的初始化协议**：

```text
audio_capture_init("/dev/audio/pcm0c")
  ├── 1. open(device, O_RDWR)           ← 打开设备节点
  ├── 2. ioctl(RESERVE)                 ← 独占设备
  ├── 3. ioctl(CONFIGURE)               ← 设置 16kHz/mono/16bit PCM
  ├── 4. ioctl(GETBUFFERINFO)           ← 查询驱动支持的缓冲区数量和大小
  ├── 5. mq_open()                      ← 创建消息队列（用于驱动通知）
  ├── 6. ioctl(REGISTERMQ)              ← 将 MQ 注册给驱动
  ├── 7. 循环 N 次:
  │     ioctl(ALLOCBUFFER) → ioctl(ENQUEUEBUFFER)  ← 分配并上交空缓冲
  └── 8. ioctl(START)                   ← 启动采集
```

**同步读封装**（`audio_capture_read`）：

```c
// 对外：阻塞的 read 接口
ssize_t audio_capture_read(int16_t *samples, size_t sample_count) {
    while (copied < sample_count) {
        // 当前缓冲用完了 → 还给驱动 → 阻塞等下一个
        if (g_current_buffer == NULL || g_current_offset >= nbytes) {
            enqueue_buffer(g_current_buffer);    // 归还空缓冲
            wait_for_buffer();                   // 阻塞等待 MQ 通知
        }
        // 从当前缓冲拷贝数据
        take = min(remaining, available);
        memcpy(samples + copied, buffer + offset, take * 2);
        copied += take; offset += take * 2;
    }
}
```

**MQ 消息处理**（`wait_for_buffer`）：

```c
static int wait_for_buffer(void) {
    for (;;) {
        mq_receive(g_audio_mq, &message, sizeof(message), &priority);
        if (message.msg_id == AUDIO_MSG_DEQUEUE) {
            // 驱动返回了一个填满的缓冲区
            g_current_buffer = message.u.ptr;
            g_current_offset = 0;
            return 0;
        }
        if (message.msg_id == AUDIO_MSG_COMPLETE || AUDIO_MSG_STOP) {
            return -EPIPE;   // 采集结束
        }
    }
}
```

**缓冲区轮转（Ping-Pong 模式）**：

```text
8 个 ap_buffer 在"应用"和"驱动"之间轮转：

  应用持有: [空]          → enqueue →
  驱动持有: [填充中...]   → 填满后通过 MQ 返回 →
  应用持有: [满]          → 消费 →
  应用持有: [空]          → enqueue →
  驱动持有: [填充中...]   → ...

每个缓冲的生命周期：FREE → ALLOCATED → ENQUEUED → FILLING → DEQUEUED → ENQUEUED → ...
```

### 3.1 全局静态数组 —— 嵌入式内存管理的基石

### 3.2 goto cleanup 错误处理模式

**出现位置**：[audio_event_main.c:372-387](../main/audio_event_main.c#L372-L387)

```c
int main(int argc, char *argv[]) {
    ret = event_classifier_init();       // 1
    if (ret < 0) return EXIT_FAILURE;

    ret = feature_extract_init();        // 2
    if (ret < 0) { event_classifier_deinit(); return EXIT_FAILURE; }

    ret = event_alert_init();            // 3
    ret = audio_source_open();           // 4
```

- 替代 `if-else` 深层嵌套（"箭头代码"）——更扁平、更可读
- 释放顺序必须是初始化的**严格逆序**，否则可能释放掉还被依赖的资源

### 3.3 环形缓冲区的两段 memcpy 实现

**出现位置**：[audio_event_main.c:177-188](../main/audio_event_main.c#L177-L188)

```c
// 从环形缓冲区取出一段连续的 16000 样本窗口
static void ring_copy_window(size_t write_position) {
    size_t tail = AUDIO_EVENT_CLIP_SAMPLES - write_position;

    // 第一段：从 write_position 到数组末尾
    memcpy(g_audio_window, &g_audio_ring[write_position],
           tail * sizeof(int16_t));

    // 第二段：从数组开头到 write_position（仅在需要时）
    if (write_position > 0) {
        memcpy(&g_audio_window[tail], g_audio_ring,
               write_position * sizeof(int16_t));
    }
}
```

**涉及的 C 语言知识点**：

- 这里用 `memcpy` 而非 `memmove`：源和目的地址绝不重叠（`g_audio_ring` vs `g_audio_window` 是独立数组），`memcpy` 可被优化为 SIMD 指令
- `sizeof(int16_t)` 正确计算了类型大小（2 bytes），不会因为平台差异出错
- 两段拷贝策略是环形缓冲"取连续窗口"的标准做法——不需要锁定或双缓冲

### 3.4 位操作实现小端序解析

**出现位置**：[audio_file.c:18-27](../audio/audio_file.c#L18-L27)

```c

    return (uint16_t)value[0] | ((uint16_t)value[1] << 8);
}

static uint32_t read_le32(const uint8_t *value) {
    return (uint32_t)value[0] | ((uint32_t)value[1] << 8)
         | ((uint32_t)value[2] << 16) | ((uint32_t)value[3] << 24);
```

**涉及的 C 语言知识点**：

- 显式 `(uint16_t)` 转型防止整数提升（integer promotion）导致的意外宽度
- 这是独立于 `<arpa/inet.h>` (POSIX) 的实现——适用于可能没有完整 POSIX 头文件的嵌入式环境
- 不依赖主机字节序，保证跨平台可移植性（在 big-endian MCU 上也正确）

### 3.5 for(;;) 循环 + ioctl 实现短读重试

**出现位置**：[audio_file.c:29-56](../audio/audio_file.c#L29-L56)

```c
static int read_exact(int fd, void *buffer, size_t size) {
    uint8_t *cursor = buffer;
    while (size > 0) {
        ssize_t count = read(fd, cursor, size);
        if (count == 0) return -ENODATA;   // EOF 提前
        if (count < 0) {
            if (errno == EINTR) continue;   // 被信号中断 → 重试
            return -errno;
        }
        cursor += count;  // 指针算术：移动写入位置
        size -= count;    // 递减剩余字节
    }
    return 0;
}
```

**涉及的 C 语言知识点**：

- 这是 POSIX `read()` 的正确用法 —— 它不保证一次返回所有请求的字节
- `EINTR` 重试是 `read` 在信号环境下的标准实践
- 指针算术 `cursor += count` 配合 `uint8_t *` 确保字节级增量
- `for(;;)` = `while(true)` 在 C99 前的标准写法（C99 前没有 `bool`）

## 4. 嵌入式系统实现

### 4.1 NuttX Sim 原理：编译为 Linux 进程的 RTOS

**不是虚拟机**。NuttX Sim (`sim:tflm`) 将整个 NuttX（内核 + 驱动 + 应用）编译为一个 Linux ELF 可执行文件。

```text
传统 MCU 运行方式：
  NuttX 任务 → ARM/RISC-V 指令 → 物理硬件执行

Sim 运行方式：
  NuttX 任务 → setjmp/longjmp 协程 → Linux 进程 → x86 指令
```

**关键机制**：

| 概念 | MCU 上 | Sim 上 |
|---|---|---|
| 任务切换 | 硬件上下文切换（PendSV） | `setjmp/longjmp` |
| 时钟中断 | 硬件 SysTick Timer | Linux `SIGALRM` 信号 |
| 内存分配 | 物理 RAM | 宿主 `malloc` |
| 文件 I/O | SPI Flash + 文件系统 | 宿主 `open/read/write` |
| 音频 I/O | I2S/PDM codec | 宿主 ALSA PCM |

**Sim 的开发优势**：

1. **极速编译-运行循环**：`make && ./nuttx`，无需烧录
2. **GDB 原生调试**：`gdb ./nuttx`，无需 JTAG 探针
3. **ASan/Valgrind** 可检测内存错误（在真实 MCU 上极难发现）
4. **CI 友好**：无硬件依赖

**Sim 的边界**：

- ❌ 不能验证真实音频硬件时序（I2S 时钟、DMA 传输延迟）
- ❌ 不能测量真实功耗和 MCU 负载
- ❌ 堆栈大小在 Sim 上几乎无限（Linux 分配），无法检测栈溢出

### 5.1 C 语言基础

**Q1: `static` 在嵌入式 C 中的典型用法？在项目中找到 3 个不同的使用场景。**

**A**：

**Q2: `memcpy` 和 `memmove` 的区别？项目中为什么 `ring_copy_window` 用 `memcpy` 而非 `memmove`？**

**A**：

- `memcpy`：不保证正确处理重叠区域。性能更优（可直接用 SIMD）
- `memmove`：保证正确处理重叠区域（内部先检查方向再拷贝）
- `ring_copy_window` 中源（`g_audio_ring`）和目标（`g_audio_window`）是**独立的全局数组**，地址空间永不重叠 → 用 `memcpy` 更高效

```c
// 用 memcpy 对 —— g_audio_ring 和 g_audio_window 是不同内存区域
memcpy(g_audio_window, &g_audio_ring[write_pos], tail * sizeof(int16_t));

// 如果用 memmove 也对，但多了不必要的重叠检查
```

---

**Q3: 为什么 `g_audio_block` 是 512 个 `int16_t` 而不是其他值？**

**A**：

1. `512 samples × 2 bytes = 1024 bytes`，对齐到 1KB 边界
2. 32ms 音频 @16kHz，足够小以保证主循环响应及时（read 不会阻塞太久）
3. 与 FFT 的 512 点变换相同值（巧合，但方便记忆）
4. 小于 `CONFIG_AUDIO_BUFFER_NUMBYTES`（通常 8192）

---

**Q4: `volatile` 和 `const` 可以同时使用吗？项目中有这样的场景吗？**

**A**：

可以。`volatile const` 表示"程序不能修改，但可能被硬件/中断改变"——常见于内存映射 I/O 寄存器。audio_event 中没有这种用法，但在 NuttX 的设备驱动头文件中广泛存在：

```c
// 内存映射寄存器的典型模式（不在 audio_event 中，但在 NuttX 驱动中）
#define UART_STATUS_REG  (*(volatile const uint32_t *)0x40001000)
```

audio_event 中的 `const` 用法：
```c
static const char *const g_event_names[] = {"knock", "cough", ...};
//     ^^^^^       ^^^^^
//     指向不可变    指针不可变 → 整个数组在 .rodata 段
```

---

### 5.2 嵌入式系统

**Q5: NuttX Audio API 为什么设计成异步的？应用层如何封装为同步？**

**A**：

**异步设计的优势**：
- 音频 I/O 的时间由硬件 I2S/DMA 时钟决定，不是软件可以"阻塞"的
- 异步模型允许驱动在硬件中断上下文中填充缓冲区，通过 MQ 通知应用
- 应用可以在等待音频数据时做其他事情（虽然 audio_event 选择了同步封装）

**同步封装策略**（audio_capture.c 的做法）：
- 维护最多 8 个 `ap_buffer` 的轮转池
- `wait_for_buffer()` 在 MQ 上阻塞等待 `AUDIO_MSG_DEQUEUE`
- `audio_capture_read()` 对外呈现标准 `read()` 语义

---

**Q6: 静态分配在嵌入式系统中为何重要？audio_event 中哪些 buffer 必须是静态的？**

**A**：

1. **确定性**：编译时就知道总内存使用，不会运行时 OOM
2. **无碎片化**：长期运行的设备中 heap 碎片化是主要问题
3. **快速启动**：BSS 段启动时清零，无需逐个构造
4. **安全审计**：linker map 文件直接显示地址和大小

audio_event 中全部 10+ 个 buffer 都是静态的：
- `g_audio_ring[16000]` — 如果动态分配，每次 run 需 32KB malloc
- `g_tensor_arena[98304]` — 96KB 的连续内存，heap 碎片化后可能无法分配
- `g_fft_state[8192]` — 必须 16 字节对齐，静态分配才能保证

---

**Q7: 从 Sim 到真实 MCU 的移植需要注意什么？**

**A**：

1. **Tensor Arena 大小调整**：Sim 上 96KB 够用，MCU 上可能需要精确裁剪至 `arena_used_bytes() + 10%`
2. **栈深度评估**：Sim 的栈无限大。MCU 上需要测量 `STACKSIZE`（当前 16384 可能需要调整）
3. **音频设备路径**：Sim 上 `/dev/audio/pcm0c`，MCU 上可能是 I2S codec 注册的不同设备名
4. **对齐保证**：`alignas(16)` 在 ARM Cortex-M 上对 CMSIS-NN 性能至关重要
5. **浮点性能**：MCU 无硬件 FPU 时，`sqrtf`/`cosf`/`logf` 会很慢——需要评估 DSP 耗时
6. **TLS 不存在**：Sim 依赖宿主 TLS，MCU 上不需要（完全离线）

---

### 5.3 信号处理与机器学习

**Q8: 为什么 FFT 输入是 512 点而非 480 点（帧长）？**

**A**：

FFT 要求输入长度为 2^n。480 不满足此要求。

方法是"零填充（zero-padding）"：
```c
memset(g_fft_input, 0, sizeof(g_fft_input));       // 512 点全清零
for (i = 0; i < 480; i++)
    g_fft_input[i] = audio * hann[i];               // 前 480 点填加权音频
                                                     // 后 32 点保持为零
```

零填充不增加频率分辨率（由 480 点有效时长决定），但通过插值使频谱"更平滑"。

---

**Q9: INT8 量化的 scale 和 zero_point 从何而来？量化误差如何评估？**

**A**：

scale 和 zero_point 是训练时通过"量化感知训练（QAT）"或"训练后量化（PTQ）"确定的，存储在 `.tflite` 文件的 FlatBuffer 元数据中。

固件端不计算这些值——初始化时从模型读取：
```c
g_input->params.scale       // 从 .tflite 自动读取
g_input->params.zero_point  // 从 .tflite 自动读取
```

量化误差 = 浮点推理输出 - INT8 量化推理输出。如果使用 QAT，误差通常在 ≤0.01 级别。

---

**Q10: 什么是 Mel 刻度？为什么不是线性频率刻度？**

**A**：

人耳对低频音高差异敏感，对高频差异迟钝。Mel 刻度模拟这种非线性感知：

- 0-500Hz：几乎线性
- 500Hz-8000Hz：越来越压缩

转换公式（O'Shaughnessy）：`mel = 1127 × ln(1 + Hz/700)`

具体到 audio_event：257 个线性 FFT bin 映射到 40 个 Mel 通道，低频段 bin 密集映射，高频段 bin 稀疏映射。这种表示更接近人耳的实际感知——对语音和声学事件识别更有效。

## 6. 技术难点与解决方案

### 6.1 特征提取的数值一致性

**挑战**：固件端 C 代码的 log-mel 输出必须与训练端 Python TensorFlow 的输出在数值上一致。任何偏差都会导致模型输出不可靠。

**根源**：训练和推理使用不同语言、不同数学库、不同浮点实现——差异可能来自：
- FFT 算法的细节（`kiss_fftr` vs NumPy/FFTPACK）
- `log` 实现的差异（`logf` vs NumPy `np.log`）
- 浮点舍入误差累积

**方案**：

1. **参数量化对齐**：所有 DSP 参数从训练脚本导出，作为编译时常量（MEL_LOWER_HZ、LOG_EPSILON、FEATURE_OFFSET、FEATURE_SCALE 全部精确匹配）
2. **预计算查表**：Hann 窗、bin→Mel 映射、Mel 频带边缘全部 precompute，避免运行时浮点发散
3. **DC bin 显式跳过**：与 TensorFlow 的 `linear_to_mel_weight_matrix` 对 DC 行置零保持一致
4. **验证方法**：同一条 WAV 分别通过 Python 和 C 前端，比较输出特征的逐元素最大/平均绝对误差，以及量化后不同元素的比例

---

### 6.2 Tensor Arena 内存调优

**挑战**：TFLM 的 `AllocateTensors()` 需要一块连续的 tensor arena。MCU 上 RAM 紧张，需要精确知道最小所需大小。

**方案**：两级调优策略

```c
// 第 1 级：先给富裕值（默认 96KB）
alignas(16) uint8_t g_tensor_arena[98304];

// 第 2 级：运行后读取实际用量
g_arena_used = g_interpreter->arena_used_bytes();
printf("[model] arena used=%zu\n", g_arena_used);

// 第 3 级：在 Kconfig 中收缩 arena_size 为 used + 安全余量（10-20%）
```

Arena 的内部布局由 TFLM 的 `MicroAllocator` 自动计算——它从头遍历计算图，在共享 arena 上排布所有张量，相邻节点复用已不需要的中间张量。

---

### 6.3 环形缓冲区的 Hop 参数约束

**挑战**：`CONFIG_EXAMPLES_AUDIO_EVENT_HOP_MS` 可以是 20-1000ms 中任意值。但部分值会导致窗口不对齐。

**方案**：运行时校验

```c
samples_until_inference = AUDIO_EVENT_SAMPLE_RATE
                         * CONFIG_EXAMPLES_AUDIO_EVENT_HOP_MS / 1000;

if (samples_until_inference == 0 ||
    samples_until_inference > AUDIO_EVENT_CLIP_SAMPLES) {
    // hop 太小（<1ms 导致 trunc 到 0）或超过窗口 → 拒绝
    return -EINVAL;
}
```

当 hop 不能整除 1000 时（如 300ms），存在截断误差，但每个窗口的计算独立——没有累积相位误差。窗口始终以当前 write_position 为中心取出最近 1 秒数据。

---

### 6.4 音频短读与设备恢复

**挑战**：真实音频设备可能因 DMA 不足、缓冲区竞争等问题返回部分数据（短读）。

**方案**：

```c
// audio_capture_read — 循环直到凑够请求量
while (copied < sample_count) {
    if (current_buffer exhausted) {
        enqueue_buffer();       // 归还空缓冲
        ret = wait_for_buffer(); // 阻塞等待新缓冲（MQ）
        if (ret < 0) return copied > 0 ? copied : ret;  // 部分数据也算成功
    }
    take = min(remaining, available);
    memcpy(dst, src, take * sizeof(int16_t));
    copied += take;
}
```

- 等待期间 `mq_receive` 可能被 `EINTR` 中断 → 重试
- 如果已拷贝了部分数据但设备停止 → 返回已拷贝的数量（而非立即报错）
- 主循环中 `count == 0` 被识别为 EOF → 正常退出而非报错

---

### 6.5 模型算子的精确注册

**挑战**：TFLM 的 `AllOpsResolver` 约 100KB+ ROM，MCU 上不可接受。必须精确注册模型需要的算子。

**方案**：

1. 从模型 FlatBuffer 遍历 `operator_codes` 确定所需的 9 类算子
2. 使用 `MicroMutableOpResolver<9>` 精确注册
3. 注册结果检查：每个 `Add*` 返回 `kTfLiteOk` 确认算子可用

```c
static tflite::MicroMutableOpResolver<9> resolver;
if (resolver.AddShape() != kTfLiteOk ||
    resolver.AddConv2D() != kTfLiteOk ||
    // ... 全部 9 个
    resolver.AddSoftmax() != kTfLiteOk) {
    return -EINVAL;  // 编译时缺少某个算子实现
}
```

**验证方法**：用 Netron 可视化 `.tflite` 文件，手动确认注册列表覆盖所有节点。

# ESP32-S3-BOX-3 项目烧录与 audio_event 测试

本文按“固件能启动 -> 应用能运行 -> 音频设备存在 -> 麦克风数据可信 -> 模型输出可信”的顺序验收。不要一上来就根据分类结果判断模型好坏，真实板端最常见的问题仍然是设备节点、I2S/codec、通道、采样率或 PCM 质量。

## 1. 构建目标

板级配置路径：

```text
vendor/espressif/boards/esp32s3/esp32s3-box-3/configs/audio_event/
```

该配置应启用：

```text
CONFIG_ESP32S3_BOX_AUDIO=y
CONFIG_EXAMPLES_AUDIO_EVENT=y
CONFIG_EXAMPLES_AUDIO_EVENT_DEVPATH="/dev/audio/pcm_in1"
CONFIG_EXAMPLES_AUDIO_EVENT_ARENA_SIZE=32768
CONFIG_TFLITEMICRO=y
CONFIG_MATH_KISSFFT=y
```

在 openvela 根目录构建：

```bash
cd /home/arongw/openvela
source build/envsetup.sh
./build.sh vendor/espressif/boards/esp32s3/esp32s3-box-3/configs/audio_event/ -j8
```

构建成功后再进入烧录步骤。若已经确认 `nuttx.bin` 是最新产物，可以直接从第 2 节开始。

## 2. 烧录固件

先确认串口。ESP32-S3-BOX-3 常见为 `/dev/ttyACM0`，也可能是 `/dev/ttyUSB0`：

```bash
ls /dev/ttyACM* /dev/ttyUSB*
```

烧录：

```bash
cd /home/arongw/openvela/nuttx
make flash ESPTOOL_PORT=/dev/ttyACM0 ESPTOOL_BAUD=921600
```

如果串口是 `/dev/ttyUSB0`，替换 `ESPTOOL_PORT` 即可。

遇到 `Permission denied` 时，先用临时方案确认流程：

```bash
sudo chmod a+rw /dev/ttyACM0
```

长期方案是把当前用户加入 `dialout` 组后重新登录。

## 3. 进入 NSH

连接串口：

```bash
picocom -b 115200 /dev/ttyACM0
```

退出 `picocom`：先按 `Ctrl-A`，再按 `Ctrl-X`。

进入 NSH 后先检查基础状态：

```nsh
help
audio_event --help
free
```

能看到 `audio_event` 命令，说明应用已经注册进系统。

## 4. 模型冒烟测试

先测模型本身，不依赖麦克风：

```nsh
audio_event --model-smoke
```

期望看到类似输出：

```text
=== Audio Event Detection ===
[model] arena=32768 used=...
[infer] t=0 ms class=... probs_permille=[...]
```

这一步只证明 TFLite Micro、模型数组、算子注册、Tensor Arena 和 int8 输入输出链路可运行。它不能证明麦克风采集正常。

## 5. 音频设备节点检查

检查 `/dev/audio`：

```nsh
ls /dev
ls /dev/audio
```

当前板级 bringup 的目标节点是：

```text
/dev/audio/pcm_in1
```

如果 `/dev/audio` 不存在，优先查 `CONFIG_ESP32S3_BOX_AUDIO`、ES7210 初始化和 I2S RX 注册。  
如果 `/dev/audio` 存在但没有 `pcm_in1`，优先查设备命名、`board_i2sdev_initialize(ESP32S3_I2S1, false, true)` 是否执行成功。

## 6. 麦克风单次测试

第一次真实麦克风测试建议打开 PCM 统计：

```nsh
audio_event --device /dev/audio/pcm_in1 --audio-stats --once
```

`--once` 会在收满第一个 1 秒窗口并完成一次推理后退出。期望看到两类输出：

```text
[audio_stats] t=1000 ms min=... max=... mean=... rms=... zero=.../16000
[infer] t=1000 ms class=... probs_permille=[...]
```

先看 `audio_stats`，再看分类：

| 现象 | 优先怀疑方向 |
|---|---|
| `zero` 接近 16000 | 没采到数据、DMA 未填充、codec 未出声 |
| `min/max` 长期接近 0 | 麦克风静音、通道不对、增益太低 |
| `min/max` 经常贴近 `-32768/32767` | 增益过高或削波 |
| `mean` 绝对值很大 | 直流偏置或格式解释错误 |
| `rms` 有变化但分类不变 | 特征/模型校准或阈值问题 |

如果 `--model-smoke` 正常但这一步失败，问题通常不在模型加载，而在 ES7210、I2S RX、设备节点或 PCM 格式。

## 7. 连续场景测试

设备模式下不要使用 `--repeat` 控制次数；当前代码里 `--repeat N` 只用于文件输入重复播放。真实麦克风连续测试直接运行：

```nsh
audio_event --device /dev/audio/pcm_in1 --audio-stats
```

手动测试以下场景，并记录完整串口日志：

```text
安静环境：应主要输出 silence，且不触发 ALERT
轻微背景声：应主要输出 background 或 silence
敲击/拍桌：knock 概率应明显上升，连续命中后触发 ALERT
咳嗽：cough 概率应明显上升，连续命中后触发 ALERT
其他突发声：观察是否误报 knock/cough
```

当前阈值来自模型元数据，默认是 knock/cough 概率达到 0.75 且连续 2 次命中后触发，冷却时间 1500 ms。真实设备打通后还需要用板端采集数据重新扫描阈值，不要只看离线训练集准确率。

## 8. 文件模式回归测试

如果能把 16 kHz mono PCM16 或 WAV 放到板端文件系统，可以用文件模式排除麦克风影响：

```nsh
audio_event --file /data/knock.wav --once
audio_event --file /data/background.wav --once
```

文件模式下 `--repeat` 有效，例如：

```nsh
audio_event --file /data/knock.wav --repeat 20
```

文件模式用于验证滑窗、特征、模型和阈值逻辑；设备模式用于验证真实麦克风链路。

## 9. 最小验收清单

```text
[ ] 固件能烧录
[ ] 串口能进入 NSH
[ ] `audio_event --help` 正常
[ ] `audio_event --model-smoke` 成功
[ ] `/dev/audio` 存在
[ ] `/dev/audio/pcm_in1` 存在
[ ] `audio_event --device /dev/audio/pcm_in1 --audio-stats --once` 能退出且不报错
[ ] `audio_stats` 显示非全零、非削波、RMS 随声音变化
[ ] 安静、背景、knock、cough 场景的概率分布有明显差异
[ ] knock/cough 能触发 `[ALERT]`
[ ] 连续运行 1-5 分钟不崩溃、不死锁、不出现持续读失败
```

当前最关键的板端下一步是先执行：

```nsh
ls /dev/audio
audio_event --device /dev/audio/pcm_in1 --audio-stats --once
```

这两个结果可以快速判断该继续调板级音频驱动，还是进入模型特征对齐和阈值校准。

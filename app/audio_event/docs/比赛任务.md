## 一、赛题设计

参赛团队需基于单片机平台（如 DshanPixVela-DevKit V1）与数字麦克风，构建一个本地音频事件检测与告警系统。
### 初赛部分目标：

完成离线本地可运行的音频事件检测系统。


任务：
1. 离线本地闭环：完成采集 → 预处理/特征提取 → 模型识别 → 输出/告警（LED/蜂鸣器/屏幕/串口等）全流程在端侧完成；结果可验证、可重复运行。
2. 基础类别覆盖：至少支持 2 类音频事件（如玻璃破碎、咳嗽），提供事件定义与触发口径说明。
3. 可复现与工程化：提供清晰的运行/部署说明，一键运行方式，具备基本异常处理。

初赛交付物：代码仓库、可复现文档、运行演示（视频/日志）。

### 复赛部分目标：

在初赛基础上进行优化与拓展，从以下任务中自由选做，完成越多、质量越高，得分越高。

1. 类别扩展：增加 1-2 类新事件识别（如婴儿哭声、狗叫、敲门声等），给出对比数据。
2. 鲁棒性提升：提升在噪声环境、不同距离条件下的识别稳定性，给出对比数据。
3. 模型优化：量化/特征优化等降低模型体积与推理延迟，提供优化前后对比。
4. 低功耗策略：唤醒策略、采样窗口策略等，有功耗数据或对比。
5. 远程告警上报：通过 MQTT/HTTP 将告警事件上报到上位机或手机端。
6. 语音关键词识别：实现对 2-3 个自定义关键词的本地识别（如"救命""帮助"等）。
7. 开发板适配（加分项）：自行选择开发板适配 openvela，在真实硬件上运行并演示。适配代码需提交至代码仓库，附适配说明文档。成功适配并提交可获得额外加分。

复赛交付物：代码仓库、复赛增量说明文档、演示视频/日志。

## 三、评审标准框架
### 初赛评审规则

1. 功能完整性（50%）  

    闭环实现可用（25%）：采集 → 识别 → 告警可重复运行
    至少 2 类事件识别有效（15%）：事件定义与触发口径清晰
    异常处理与稳定运行（10%）

2. 工程化与开源合规（30%）  

    一键运行 + 复现信息完备（20%）
    开源协议与合规（10%）：LICENSE/NOTICE/第三方依赖声明齐全

3. 文档与性能数据（20%）  

    README 完整（快速开始、项目结构）
    延迟与误报/漏报基础数据

### 复赛评审规则

1. 任务完成度与效果（50%）  

    按选做任务数量与质量综合评分

2. 现场/统一用例表现（25%）  

    统一用例识别成功率
    多轮运行无崩溃，异常可恢复

3. 工程化与文档（25%）  

    合规与溯源（8%）
    工程化与可复现（9%）
    复赛增量文档质量（8%）

4. 开发板适配  

    成功适配 openvela 开发板并在真实硬件上运行演示，提交适配代码与说明文档，可获得额外加分

1. 基于单片机平台实现端侧离线音频事件检测全流程系统
2. 基础音频事件分类识别与本地告警功能开发

## 五、当前项目落地对照

> 本节是 `audio_event` 项目对赛题的实施解释，不改变前述赛事原始要求。

### 初赛基线

| 赛题要求 | 当前项目方案 | 状态 |
|---|---|---|
| 端侧离线闭环 | 麦克风 -> 1 秒缓存 -> 49x40 log-mel -> TFLite Micro -> 本地告警 | 开发中 |
| 至少 2 类事件 | `knock`、`cough` | 模型已覆盖，板端待验证 |
| 非目标声音抑制 | `background`、`silence` 两个拒识类别 | 模型已覆盖，阈值待实测 |
| 一键运行 | NSH 命令 `audio_event` | 应用骨架已有，完整链路待实现 |
| 异常处理 | 音频短读重试、设备恢复、模型初始化失败退出 | 待完善 |
| 性能数据 | 误报、漏报、特征耗时、推理耗时、RAM、连续运行 | 离线指标已有，板端数据待补 |

当前 INT8 模型的离线测试准确率为 88.65%，误报率为 2.40%，漏报率为 17.48%。这些数据只作为模型基线；最终提交必须补充目标开发板和真实麦克风条件下的事件级结果。

### 复赛候选方向

初赛闭环稳定后，优先选择以下任务：

1. 补充不同距离、噪声和设备数据，降低咳嗽漏报。
2. 静态化模型 reshape，减少算子和 Tensor Arena 占用。
3. 增加 1-2 类音频事件并重新评估拒识能力。
4. 增加静音能量门控，比较完整推理前后的功耗。
5. 在本地告警之外增加 MQTT/HTTP 非阻塞上报。
5. openvela 平台开发板硬件适配与部署验证

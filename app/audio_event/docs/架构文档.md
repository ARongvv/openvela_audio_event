# Audio Event Detection 架构文档

> 版本：1.1  
> 更新日期：2026-06-20  
> 状态：以 `model/model_int8.tflite` 和 `model/metadata.json` 为当前模型基线

具体实现、模拟器配置和测试步骤见 [开发文档.md](开发文档.md)。

## 1. 项目目标

`audio_event` 是运行在 openvela（NuttX）上的离线音频事件检测应用。初赛目标是在单片机和数字麦克风上完成以下本地闭环：

```text
音频采集 -> 1 秒音频缓存 -> log-mel 特征 -> TFLite Micro 推理
         -> 事件判定与去抖 -> 串口/LED/蜂鸣器告警
```

当前模型识别两个目标事件：

- `knock`：敲击或敲门声
- `cough`：咳嗽声

`background` 和 `silence` 是拒识类别，不触发告警。两个目标事件已经满足比赛“至少支持 2 类音频事件”的要求。

## 2. 设计基线

训练模型是部署接口的唯一事实来源。固件端的采样、特征、量化和类别顺序必须与下表一致。

| 项目 | 当前模型契约 |
|---|---|
| 采样率 | 16000 Hz |
| 输入时长 | 1000 ms，16000 个单声道采样点 |
| 分析窗口 | 30 ms |
| 窗口步长 | 20 ms |
| 特征 | TensorFlow 风格 log-mel |
| 特征形状 | `[49, 40, 1]` |
| 模型输入 | INT8，`[1, 1960]` |
| 输入量化 | scale `0.101961`，zero point `-128` |
| 模型输出 | INT8，`[1, 4]` |
| 输出量化 | scale `0.00390625`，zero point `-128` |
| 类别顺序 | `knock, cough, background, silence` |
| 模型大小 | 11376 bytes |
| 参数量 | 1548 |

旧版“每 512 个采样点提取 13 维 MFCC、逐帧分类”的设计不再适用于当前模型。相关接口需要在实现阶段替换，不能将 13 维 MFCC 直接送入 `[1, 1960]` 的模型输入。

## 3. 分层架构

```text
main/
  负责生命周期、运行循环、错误恢复和模块编排
       |
       +-> audio/  麦克风设备、PCM 格式转换、环形缓冲区
       +-> dsp/    与训练端一致的 49x40 log-mel 前处理
       +-> model/  TFLite Micro 初始化、INT8 输入输出、模型信息检查
       +-> alert/  阈值、连续确认、冷却时间和告警设备
```

依赖方向保持单向：`main` 调用各业务层，各业务层之间不直接依赖。这样可以用固定 PCM 和黄金特征分别测试 `dsp` 与 `model`。

### 3.1 音频采集层

职责：

- 打开目标板音频设备并配置为 16 kHz、16-bit、单声道 PCM。
- 将设备数据转换为统一的 `int16_t` 或归一化浮点表示。
- 维护至少 16000 个采样点的环形缓冲区。
- 每次推理提供连续、按时间排序的 1 秒音频。
- 处理短读、超时、设备断开和重新初始化。

建议初始推理间隔为 250 ms。模型仍然观察完整 1 秒窗口，250 ms 只是相邻推理窗口的移动距离，不是 log-mel 的 20 ms 帧移。

### 3.2 特征提取层

职责：把 16000 个 PCM 样本转换为与训练端逐元素一致的 1960 个 log-mel 特征。

```text
PCM[16000]
  -> 分帧（30 ms，20 ms stride）
  -> 窗函数和频谱
  -> 40 路 Mel 滤波器组
  -> 对数变换
  -> feature[49][40]
  -> 展平 feature[1960]
```

`metadata.json` 尚未记录 FFT 点数、窗函数、频率上下限、功率谱定义、对数底数/epsilon 和归一化方式。这些参数必须从训练脚本导出，并通过同一段 WAV 的 Python/C 特征对比确认。仅凭“tensorflow_log_mel”无法保证数值一致。

### 3.3 模型推理层

TFLite Micro API 是 C++ API，因此实现文件应使用 `.cc`；对外头文件可继续通过 `extern "C"` 暴露 C 接口。

初始化流程：

1. 使用 `g_audio_event_model` 调用 `tflite::GetModel()`。
2. 校验 FlatBuffer schema 版本。
3. 注册模型实际使用的算子。
4. 使用静态 Tensor Arena 创建 `MicroInterpreter`。
5. 调用 `AllocateTensors()`。
6. 校验输入输出类型、维度和量化参数。

当前模型实际使用 9 类算子、12 个算子节点：

```text
SHAPE
STRIDED_SLICE
PACK
RESHAPE
CONV_2D
DEPTHWISE_CONV_2D
MEAN
FULLY_CONNECTED
SOFTMAX
```

Resolver 必须覆盖上述算子。Tensor Arena 先保守预留 64-96 KB，成功分配后记录 `arena_used_bytes()`，再依据目标板实测值收缩，不能把文档中的估算值当成已验证指标。

量化处理：

```text
input_int8 = clamp(round(feature / input_scale) + input_zero_point, -128, 127)
probability = (output_int8 - output_zero_point) * output_scale
```

### 3.4 事件判定与告警层

类别 ID 必须固定为：

| ID | 类别 | 是否告警 | 初始阈值 |
|---:|---|---|---:|
| 0 | knock | 是 | 0.75 |
| 1 | cough | 是 | 0.75 |
| 2 | background | 否 | - |
| 3 | silence | 否 | - |

初始策略采用模型元数据中的建议：目标类别概率达到阈值且连续 2 次推理满足条件时触发。还应增加 1-2 秒冷却时间，避免一次持续事件重复告警。

阈值是部署起点，不是最终结论。板端采集链路打通后，应分别扫描 `knock` 和 `cough` 的阈值，以误报率、漏报率和现场召回率确定最终值。

## 4. 运行时流程

```text
INIT
  -> 初始化 audio/dsp/model/alert
LISTEN
  -> 持续读取 PCM 并写入环形缓冲区
WINDOW_READY
  -> 取得最近 1 秒 PCM
FEATURE
  -> 生成并量化 1960 个 log-mel 特征
INFER
  -> TFLite Micro Invoke
DECIDE
  -> 反量化、分类阈值、连续确认、冷却判断
ALERT 或 LISTEN
```

### 4.1 开发环境映射

同一业务流水线通过不同音频 source 运行：

```text
原生 Sim 文件模式：HostFS PCM ---------+
原生 Sim ALSA：     /dev/audio/pcm0c ---+-> ring buffer -> DSP -> TFLM -> alert
真实开发板：        codec/I2S/PDM ------+
```

文件 source 和设备 source 必须输出相同格式的 16 kHz、16-bit、单声道 PCM。DSP、模型和事件判定层不感知输入来自 Sim 还是真实硬件。

验证顺序固定为：黄金 INT8 特征、固定 PCM、连续 PCM、Sim ALSA、真实开发板。Goldfish/QEMU 只作为可选的系统镜像集成环境。

任何阶段失败都必须返回明确错误码。音频短读可重试；连续设备错误应重新初始化音频设备；模型初始化、Tensor 分配或模型契约检查失败应终止运行并打印原因。

## 5. 文件与构建

目标目录结构：

```text
apps/examples/audio_event/
├── main/audio_event_main.c
├── audio/audio_capture.c
├── dsp/feature_extract.c          # 实现时可按需要改为 .cc
├── model/event_classifier.cc      # TFLite Micro C++ 封装
├── model/event_classifier.h
├── model/model.cc                 # alignas(16) 的模型数组
├── model/model.h
├── model/model_int8.tflite        # 训练产物，便于检查
├── model/metadata.json            # 模型契约
└── alert/event_alert.c
```

构建系统需要完成：

- 将 `model/model.cc` 和 C++ 推理实现加入 CMake/Make 源文件。
- 依赖 `TFLITEMICRO`、`AUDIO` 和实际前处理所需的 FFT 库。
- 确保模型数组为 `const` 且至少 16 字节对齐。
- 不使用 `AllOpsResolver`，只注册模型所需算子。

## 7. 验收条件

### 7.1 模拟器开发关卡

- 原生 Sim 可以使用黄金 INT8 输入完成 TFLM Invoke。
- 固定 PCM 的 log-mel 和分类结果与训练端一致。
- 连续文件流可以验证滑窗、阈值、去抖和事件合并。
- Sim ALSA 可以通过 `/dev/audio/pcm0c` 连续采集并运行 30 分钟。
- 模拟器结果标记为功能验证，不作为 MCU 性能或功耗结论。

### 7.2 初赛闭环

- 真实麦克风完成采集、特征、推理和本地告警。
- `knock`、`cough` 均可重复触发，背景和静音不告警。
- 连续运行无崩溃，音频短读能够恢复。
- 提供一键构建/运行说明和演示日志。

### 7.3 模型与性能

- Python 与固件端 log-mel 使用同一 WAV 时误差处于量化容忍范围。
- 固件端输出与桌面 TFLite 对同一测试向量的类别一致。
- 记录模型大小、Tensor Arena、特征耗时、推理耗时、端到端延迟。
- 分别记录两类事件的 Precision、Recall、误报率和漏报率。

## 8. 架构决策

1. 以当前 INT8 模型契约为准，不再维护单帧 13 维 MFCC 路线。
2. `knock` 和 `cough` 是目标事件，`background` 和 `silence` 是拒识类别。
3. 先用固定测试向量验证特征与推理，再接真实麦克风，便于定位问题。
4. 阈值按类别独立调优，不使用“argmax 后所有非零 ID 都告警”的逻辑。
5. 所有性能数字必须区分离线评估和目标板实测。

# 异常处理说明

本文档描述 `audio_event` 系统各模块的已知异常场景、代码中的处理策略及排查建议。

---

## 一、异常处理总览

| 模块 | 异常类别 | 处理策略 |
|------|----------|----------|
| 音频采集 `audio_capture` | 设备不可用 | 返回 `-errno`，主循环退出 |
| 音频采集 `audio_capture` | 驱动 buffer 信息查询失败 | 回退到本地 ap_buffer 分配 |
| 音频采集 `audio_capture` | buffer 数量超出上限 | 返回 `-E2BIG` |
| 音频采集 `audio_capture` | 消息队列创建失败 | 返回 `-errno`，清理已分配资源 |
| 音频采集 `audio_capture` | 读取时驱动返回 `AUDIO_MSG_COMPLETE/STOP` | 返回 `-EPIPE` |
| 音频采集 `audio_capture` | 部分读取成功后再遇错误 | 返回已读取的 sample 数 |
| 音频文件 `audio_file` | 文件格式不匹配 | 返回 `-ENOTSUP` 或 `-EINVAL` |
| 音频文件 `audio_file` | 文件内容不足一窗 | 返回 0（EOF） |
| 特征提取 `feature_extract` | KISSFFT 状态内存不足 | 返回 `-ENOMEM`，打印所需/实际字节数 |
| 特征提取 `feature_extract` | 参数校验失败 | 返回 `-EINVAL` |
| 模型推理 `event_classifier` | TFLite 版本不匹配 | 返回 `-EINVAL` |
| 模型推理 `event_classifier` | tensor arena 不足 | 返回 `-ENOMEM` |
| 模型推理 `event_classifier` | 输入/输出 tensor 维度不符 | 返回 `-EINVAL` |
| 模型推理 `event_classifier` | Invoke 执行失败 | 返回 `-EIO` |
| 检测器 `event_detector` | 参数校验失败 | 返回 `-EINVAL`，detection 结构体置零 |
| 告警 `event_alert` | 硬件设备未连接 | 串口输出作为最低可用告警通道 |
| UI `audio_event_ui` | LVGL/LCD 初始化失败 | 主循环继续运行，不阻塞推理 |
| 主循环 | 音频读失败 | 清理资源，返回 `EXIT_FAILURE` |
| 主循环 | 输入在一窗完成前耗尽 | 返回 `-ENODATA` |
| 主循环 | hop 参数非法 | 返回 `-EINVAL` |

---

## 二、各模块异常详解

### 2.1 音频设备采集 (`audio/audio_capture.c`)

#### 设备节点不存在 / 无法打开

```text
[audio] cannot open /dev/audio/pcm_in1: -2
```

**现象**：`open()` 返回错误，`audio_capture_init()` 返回 `-errno`，主循环打印 `[app] audio read failed` 后退出。

**常见原因**：
- I2S 驱动未正确注册（真机上 `CONFIG_ESP32S3_I2S1_RX` 未启用）
- 设备路径与 defconfig 中 `CONFIG_EXAMPLES_AUDIO_EVENT_DEVPATH` 不一致
- ES7210 初始化早于 I2S 时钟稳定（ESP32-S3-BOX-3），导致设备注册失败

**排查**：
```text
nsh> ls /dev/audio
```
确认设备节点是否存在。对于 BOX-3，先跑 `audio_test --device /dev/audio/pcm_in1 --channels 2 --seconds 10 --es7210` 验证初始化时序。

#### 驱动 buffer 信息查询失败

```text
[audio] get buffer info failed: -95, fallback to local buffers
[audio] buffer info: nbuffers=4 size=2048 bytes
```

**现象**：`AUDIOIOC_GETBUFFERINFO` ioctl 失败（模拟器上常见），代码自动回退到本地分配模式：用 `apb_alloc()` 替代 `AUDIOIOC_ALLOCBUFFER`，buffer 数量和大小使用 Kconfig 中的配置值（`CONFIG_AUDIO_NUM_BUFFERS` / `CONFIG_AUDIO_BUFFER_NUMBYTES`），上限为 4 个 × 2048 字节。

**影响**：正常工作，性能略降（本地 buffer 不共享 DMA 内存）。日志中包含 `fallback to local buffers` 信息性提示，**不是错误**。

#### buffer 数量超出上限

```text
[audio] unsupported buffer count: 16 max=8
```

**现象**：驱动返回的 `buffer_info.nbuffers` 超过 `AUDIO_CAPTURE_MAX_BUFFERS`（8），或为 0。返回 `-E2BIG`。

**常见原因**：驱动配置异常。检查 `CONFIG_AUDIO_NUM_BUFFERS` 和 `CONFIG_I2S_DMADESC_NUM` 是否在合理范围（建议 2–8）。

#### 消息队列创建失败

```text
[audio] mq_open failed: -24
```

**现象**：`mq_open()` 失败，通常因为消息队列名冲突或系统 mqueue 资源耗尽。返回 `-errno`，已分配资源通过 `goto fail` 路径全部释放（`audio_capture_deinit()`）。

**排查**：检查是否有其他进程使用了同名消息队列 `/audio_event_<pid>`（极少发生）。

#### 采集过程中驱动终止流

**现象**：`wait_for_buffer()` 收到 `AUDIO_MSG_COMPLETE` 或 `AUDIO_MSG_STOP` 消息。返回 `-EPIPE`。

**常见原因**：
- 驱动端发生了不可恢复的 I2S 错误（如 FIFO 溢出）
- 外部调用了 `AUDIOIOC_STOP`

**处理**：`audio_capture_read()` 在返回错误前会先把本次已读取的 sample 数返回给调用者（`return copied > 0 ? copied : ret`）。这意味着如果在一个 block 的读取中已经读到了部分数据，不会白白丢弃。

#### 部分读取成功 + 后续错误

`audio_capture_read()` 使用 `while (copied < sample_count)` 循环，每次最多读 512 个 sample。如果在循环中间某次 `wait_for_buffer()` 失败，函数会优先返回已经读取的有效数据（`return copied > 0 ? copied : ret`），避免丢弃有效数据。

#### 参数校验

`audio_capture_init()` 中 `device_path == NULL || g_audio_fd >= 0` 时返回 `-EINVAL`，防止重复初始化或空指针。

`audio_capture_read()` 中 `g_audio_fd < 0 || !g_audio_started || samples == NULL || sample_count == 0` 时返回 `-EINVAL`，防止在未初始化状态下读取。

### 2.2 音频文件输入 (`audio/audio_file.c`)

#### WAV 格式不匹配

```text
[file] WAV must be PCM, 16 kHz, mono, 16-bit
```

**现象**：WAV 文件的采样率、通道数或位深度与期望不符。返回 `-ENOTSUP`，`audio_file_open()` 自动关闭文件句柄。

**要求**：文件必须是 PCM 格式（`AudioFormat=1`），16 kHz，mono，16-bit。可使用 `ffmpeg` 转换：
```bash
ffmpeg -i input.wav -acodec pcm_s16le -ac 1 -ar 16000 output.wav
```

#### 非 WAV 原始 PCM 文件大小异常

- 文件大小为奇数 → 返回 `-EINVAL`（PCM 16-bit 必须为偶数字节）
- `audio_file_read()` 的 `sample_count` 不能超过 `FILE_READ_MAX_SAMPLES`（512）→ 否则返回 `-EINVAL`

#### 文件内容不足一个完整窗口

```text
[app] input ended before one full window
```

**现象**：文件总 sample 数小于 `AUDIO_EVENT_CLIP_SAMPLES`（16000）。返回 `-ENODATA`。

**处理**：主循环会检测 `windows > 0` 的情况——如果已经处理了至少一个完整窗口，正常返回 0（成功）；否则返回 `-ENODATA`。

#### 文件读到末尾

**正常 EOF**：`audio_file_read()` 返回 0，主循环正常退出。

**Repeat 模式**：`--repeat N` 时，文件读到末尾会自动 `lseek` 回到数据起始位置重新读取。最后一次 repeat 结束时返回 0。

### 2.3 特征提取 (`dsp/feature_extract.c`)

#### KISSFFT 状态内存不足

```text
[feature] FFT state needs 16384 bytes, have 8192
```

**现象**：`kiss_fftr_alloc()` 需要的内存超出静态分配的 `g_fft_state[8192]`。返回 `-ENOMEM`，主循环在 `feature_extract_init()` 阶段就退出。

**处理**：`feature_extract.c` 中 `FFT_STATE_BYTES` 预置为 8192。如果 KISSFFT 版本或配置导致需要更大的状态空间，错误信息直接打印所需值和实际值，方便开发者调整。

#### 参数校验

`feature_extract_compute()` 会校验：
- `g_fft != NULL`（未初始化）
- `samples != NULL`、`features != NULL`（空指针）
- `sample_count == AUDIO_EVENT_CLIP_SAMPLES`（窗口大小不匹配）
- `feature_count == AUDIO_EVENT_FEATURE_SIZE`（特征维度不匹配）

任一失败返回 `-EINVAL`。

### 2.4 模型推理 (`model/event_classifier.cc`)

#### TFLite 版本不匹配

```text
[model] schema mismatch: model=5 runtime=6
```

**现象**：`model.cc` 中嵌入的模型文件版本与 NuttX SDK 中的 TFLite Micro 运行时版本不一致。返回 `-EINVAL`。

**排查**：确认 `model_int8.tflite` 是在与 SDK 中 TFLite Micro 版本兼容的工具链下生成的。模型版本号存储在 `model.cc` 中 `g_audio_event_model` 数组的前几个字节。

#### Tensor arena 不足

```text
[model] AllocateTensors failed, arena=32768
```

**现象**：`interpreter.AllocateTensors()` 失败，当前 arena 大小不够。返回 `-ENOMEM`。

**处理**：arena 大小由 `CONFIG_EXAMPLES_AUDIO_EVENT_ARENA_SIZE` 控制（默认 32768，范围 32768–262144）。需要增大该配置值。注意：arena 的 16 字节对齐要求已由 `alignas(16)` 满足。

#### 输入/输出 tensor 不匹配

```text
[model] expected int8 input with 5880 elements, got type=0
[model] expected int8 output with 4 elements, got type=0
```

**现象**：模型推理初始化阶段检查输入/输出 tensor 的 dtype 和元素计数。如果模型的输入维度不是 `[49][40][3]`（5880 个 int8）、输出不是 `[4]` 个 int8，返回 `-EINVAL`。

**排查**：确认 `model_int8.tflite` 与 `audio_event_config.h` 中的 `FEATURE_SIZE`、`CLASS_COUNT` 一致。

#### Invoke 执行失败

```text
[model] Invoke failed
```

**现象**：`interpreter.Invoke()` 返回非 `kTfLiteOk`。返回 `-EIO`。

**可能原因**：
- Tensor 数据越界（特征值定量化后超出 [-128, 127]——但代码已在 `event_classifier_predict()` 中做了 `std::lround() + clamp`）
- 内存损坏（arena 大小不足但 AllocateTensors 勉强通过）

**排查**：开启 TFLite Micro 调试输出（`CONFIG_TFLITEMICRO_DEBUG=y`），查看详细错误信息。

#### 浮点转 int8 量化钳位

```c++
long value = std::lround(features[i] / g_input->params.scale) +
             g_input->params.zero_point;
if (value < -128) value = -128;
else if (value > 127) value = 127;
```

特征值在送入模型前经 `lround` + clamp 到 `[-128, 127]`。如果特征值超出范围且发生钳位，当前代码**静默处理**（不打印警告）。如果怀疑特征分布异常，可以临时加日志检查有多少值触发了钳位。

#### 概率输出值域保护

`read_output()` 中 `(int8_value - zero_point) * scale` 的计算结果直接写入 probabilities 数组。`event_alert_fire()` 对 confidence_permille 做了 `[0, 1000]` 的二次钳位，防止因量化误差导致的微小越界。

### 2.5 检测器 (`detector/event_detector.c`)

#### 参数校验

`event_detector_update()` 检查：
- `probabilities != NULL`、`detection != NULL`（空指针）
- `class_count == AUDIO_EVENT_CLASS_COUNT`（类别数不匹配，如未来改了模型但未更新）

任一失败返回 `-EINVAL`，并保证 `detection->fired = false`（调用方可安全判断）。

#### 冷却期内的时间戳倒流

如果 `timestamp_ms < g_cooldown_until_ms`，检测器静默返回（不更新 candidate 也不重置）。这不依赖于单调递增的时间戳——如果系统时钟跳变导致时间戳倒退，冷却可能异常延长。在 NuttX 环境下，timestamp 来自 `total_samples * 1000 / SAMPLE_RATE`，不受系统时钟影响，因此此场景不会发生。

### 2.6 告警输出 (`alert/event_alert.c`)

#### LED / 蜂鸣器不可用

`event_alert_init()` 中的 `TODO: open /dev/userleds or /dev/pwm0 for buzzer` 表明当前**还未实现硬件告警**。告警仅通过 `printf()` 串口输出。

```text
[ALERT] *** cough detected *** (confidence=777/1000)
```

这是**有意的最小可用告警设计**——串口输出总是可用的，不依赖额外的硬件驱动。线上评审可以通过串口日志验证告警功能，真机上 LED/蜂鸣器是后续增强。

#### 空事件名保护

```c
printf("[ALERT] *** %s detected *** (confidence=%d/1000)\n",
       event_name ? event_name : "?", confidence_permille);
```

`event_name == NULL` 时输出 `"? detected"` 而不是崩溃。

---

### 2.7 UI 子系统 (`ui/audio_event_ui.c`)

#### LVGL/LCD 初始化失败

```text
[app] UI init failed, continuing without UI
```

**现象**：LVGL 初始化返回错误时，主循环**不终止**，继续运行推理和告警。串口输出 `[infer]` 和 `[ALERT]` 仍然可用。

**设计意图**：UI 是增值功能，不是核心链路。评审时即使 UI 不可用，闭环（采集→识别→告警）仍可完整验证。

---

### 2.8 主循环 (`main/audio_event_main.c`)

#### 音频读取失败

```text
[app] audio read failed: -32
```

主循环中 `audio_capture_read()` 或 `audio_file_read()` 返回负值时，打印错误码后 `break` 退出循环，进入 `cleanup:` 标签依次释放所有资源。返回 `EXIT_FAILURE`。

#### 输入在首窗完成前耗尽

```text
[app] input ended before one full window
```

`count == 0` 且 `windows == 0`（一个完整推理窗口都没完成）时，返回 `-ENODATA`。

`count == 0` 且 `windows > 0`（至少处理了一窗）时，正常退出（`ret = 0`）。

#### hop 参数非法

```text
[app] invalid hop configuration
```

`CONFIG_EXAMPLES_AUDIO_EVENT_HOP_MS` 对应的 sample 数为 0 或大于 `AUDIO_EVENT_CLIP_SAMPLES` 时触发。返回 `-EINVAL`。合法范围：20ms–1000ms。

#### 模型冒烟测试失败

`--model-smoke` 模式下，以全零特征送入模型，验证推理链路（模型加载、tensor 分配、op 执行、输出读取）是否正常。如果失败，直接返回 `EXIT_FAILURE`。冒烟成功则正常返回 `EXIT_SUCCESS`。

#### 命令行参数解析错误

```text
Unknown or incomplete option: --foo
```

`parse_options()` 返回 `-EINVAL`，打印用法信息（usage）后返回 `EXIT_FAILURE`。

## 三、资源清理保证

`main()` 中使用 `goto cleanup` + 标志位（`file_open`、`capture_open`）确保无论何种退出路径，所有资源都被正确释放：

```
cleanup:
  audio_event_ui_deinit()     // #ifdef CONFIG_EXAMPLES_AUDIO_EVENT_UI
  if (file_open) → audio_file_close()
  if (capture_open) → audio_capture_deinit()
  event_alert_deinit()
  feature_extract_deinit()
  event_classifier_deinit()
```

`audio_capture_deinit()` 内部保证：
1. 先 STOP 设备
2. 再 UNREGISTERMQ
3. 逐个 FREE buffer（区分 local buffer 和驱动 buffer）
4. RELEASE 会话
5. close fd
6. mq_close + mq_unlink

**任何一步失败都不会影响后续步骤的执行**——释放流程不回退、不因 ioctl 错误而中断。

## 四、诊断工具

### `audio_test` — 独立麦克风诊断

`audio_test` 不加载模型、不初始化 UI，只验证采集链路：

```text
nsh> audio_test --device /dev/audio/pcm_in1 --channels 2 --seconds 5
```

判断标准：
- `rms` 长期接近 0 且 zero 接近总采样数 → 驱动链路未收到数据
- 单声道全零、另一路有数据 → I2S slot/channel 配置问题
- `clip` 持续增加 → 输入增益过高或格式解释错误
- 敲击/说话时 `rms` 升高 → 采集链路可用

### `--audio-stats` — 应用内 PCM 诊断

```text
nsh> audio_event --device /dev/audio/pcm_in1 --audio-stats --once
```

在推理链路内打印每窗的 PCM 统计。用于判断麦克风数据在进入特征提取前的质量。

### `--model-smoke` — 模型冒烟测试

```text
nsh> audio_event --model-smoke
```

以全零特征送入模型，验证推理链路正常。不依赖音频输入。

# 远程告警上报方案

> 状态：HTTP 首版固件已实现；已新增不含凭据的 Wi-Fi/WAPI 联调 profile，等待板端联网与 HTTP 联调。
> 目标：在本地音频告警保持独立可用的前提下，通过 MQTT 或 HTTP 将事件异步上报至局域网上位机、服务器或手机端。

## 1. 范围与核心原则

远程上报是本地检测的附加能力，不能成为采集、推理和本地告警的前置条件：

```text
音频采集 -> 特征/模型 -> 本地判决 -> OLED/串口本地告警
                                  |
                                  +-> 非阻塞事件队列 -> MQTT/HTTP 上报任务
```

必须满足：

- 无网络、服务器不可达、认证失败或上报超时时，本地识别和本地告警仍正常运行；
- 网络 I/O 只在独立任务中执行，绝不运行在采集线程、模型推理路径或检测器临界路径中；
- 队列、重试次数和内存使用有上界，防止断网时无限堆积；
- 上报的数据最小化，不上传原始音频，除非后续另行获得用户授权并定义隐私策略；
- 初版优先实现一种协议并完整验证，另一种协议作为可插拔后端，而不是同时半成品接入。

## 2. 前置条件与部署形态

当前 `esp32s3-devkit` 音频配置已覆盖 I2S、OLED 和本地模型推理，但远程上报还需要确认并配置 Wi-Fi 驱动、网络栈、DHCP/DNS、时间同步、协议库和证书存储空间。网络能力未启用或不可用时，应用应显示 `offline`，但不能拒绝启动本地检测。

首版推荐部署于可信局域网：

```text
ESP32-S3 + audio_event
      | Wi-Fi
      v
LAN MQTT broker 或 HTTP receiver
      |
      +-> 上位机网页/日志
      +-> 手机浏览器或消息推送服务
```

手机端通常不直接作为 MCU 的 MQTT/HTTP 服务端。更可靠的形态是上位机或局域网服务器接收事件，提供网页页面；需要移动通知时，再由服务器推送到手机。

## 3. 协议选择

### 3.1 HTTP：首个最小可行版本

HTTP `POST` JSON 更容易使用本地 Web 服务、抓包工具和浏览器验证，推荐作为第一阶段实现。设备在有事件时向一个固定 URL 提交 JSON，接收端返回 `2xx` 即认为本次上报成功。

```text
POST /api/v1/audio-events
Content-Type: application/json
Authorization: Bearer <token>       # 如启用认证
```

优点：调试直观、服务端实现简单、易演示到上位机网页；缺点：连接管理和每次请求开销通常高于 MQTT。

### 3.2 MQTT：长期事件通道

MQTT 适合频繁、小消息、在线状态和多订阅者场景。建议主题格式：

```text
audio_event/<device_id>/events
audio_event/<device_id>/status
```

事件使用 QoS 1 作为候选：broker 确认收到消息后才完成本次发送。QoS 不能替代本地队列和重连策略；在断网时不得阻塞或无限重发。

优点：低开销、可被多个客户端订阅；代价：需要 broker、连接状态机、协议库和更完整的断线处理。

### 3.3 安全要求

- 演示可在受控局域网中使用 HTTP 或 MQTT 明文，但必须在文档中明确网络边界，不得宣称其适用于公网。
- 涉及公网、个人数据或长期部署时，应使用 TLS、服务端证书校验、独立设备凭据和最小权限 topic/API。
- Token、Wi-Fi 密码、broker 密码和证书不得写入源码、模型元数据、日志或演示视频；应从安全配置或受保护存储加载。

## 4. 事件数据契约

上报的是已经通过本地阈值/冷却判决的事件，不上报每个窗口的原始概率。建议 JSON：

```json
{
  "schema_version": 1,
  "event_id": "boot-7-seq-42",
  "device_id": "esp32s3-audio-01",
  "event": "cough",
  "confidence_permille": 938,
  "monotonic_ms": 6880,
  "wall_time": "2026-07-25T12:34:56+08:00",
  "firmware_version": "git-<short-sha>",
  "model_sha256_prefix": "923dae76"
}
```

HTTP 首版当前实际发送 `schema_version`、`event_id`、`device_id`、`event`、
`confidence_permille` 和 `monotonic_ms`。`wall_time` 依赖 NTP/RTC，
`firmware_version` 与 `model_sha256_prefix` 依赖构建元数据，均保留为后续
可兼容扩展字段，不能在首版测试中声称已经上报。

字段约定：

| 字段 | 必选 | 说明 |
| --- | --- | --- |
| `schema_version` | 是 | 便于服务端演进 |
| `event_id` | 是 | 重试去重用的唯一标识；由 boot ID + 单调递增序号组成 |
| `device_id` | 是 | 配置注入的匿名设备标识，不使用个人信息 |
| `event` | 是 | 本地已判决的类别，如 `knock`、`cough` 或关键词 |
| `confidence_permille` | 是 | 0–1000 的整数，避免浮点显示差异 |
| `monotonic_ms` | 是 | 设备启动后的单调时间，始终可用 |
| `wall_time` | 否 | 仅在 NTP/RTC 已同步时携带 |
| `firmware_version` | 建议 | 排查现场版本差异 |
| `model_sha256_prefix` | 建议 | 确认模型溯源 |

服务端应以 `event_id` 去重。网络恢复后的重复提交应得到幂等处理，不能在手机端产生重复告警风暴。

## 5. 固件架构

### 5.1 模块划分

```text
alert/event_alert
  -> 始终完成本地打印/OLED 告警
  -> reporter_enqueue(event)    # 常数时间、不可阻塞

reporter/
  -> 有界静态队列
  -> 网络状态机
  -> HTTP 或 MQTT 后端
  -> 超时、重试、指数退避
  -> 上报结果和统计
```

`event_alert_fire()` 只能构造小型事件记录并尝试入队；队列满时记录一次丢弃计数后立即返回。网络连接、DNS、TLS、HTTP 请求和 MQTT 重连均在 `reporter` 工作线程中完成。

### 5.2 有界队列与断网行为

首版采用 RAM 中固定长度队列。建议容量从 8–32 条事件开始，根据结构体大小和板端 RAM 实测确定。

| 场景 | 期望行为 |
| --- | --- |
| 网络正常 | 工作线程按顺序发送，成功后出队 |
| 网络断开 | 本地告警继续；工作线程按退避时间重连 |
| 服务端 5xx/超时 | 限定次数重试；不阻塞采集与推理 |
| 认证 4xx | 停止高频重试，记录错误状态，等待配置修复 |
| 队列满 | 保留最早未发送事件或按明确策略丢弃；累计 `dropped_events` |
| 设备重启 | RAM 队列可丢失；首版在文档中明确该边界 |

Flash 持久化队列可作为后续增强项，但频繁写 Flash 会影响寿命和实现复杂度。未验证前不应声称“断网事件永不丢失”。

### 5.3 重试和退避

建议使用有限重试和指数退避，例如：

```text
1 s -> 2 s -> 4 s -> 8 s -> 30 s（上限）
```

增加少量随机抖动，避免多台设备同时恢复网络时同步重连。每次网络操作必须设置连接、发送和响应超时；不得无限阻塞。

### 5.4 建议配置项

| 配置 | 示例语义 |
| --- | --- |
| `EXAMPLES_AUDIO_EVENT_REMOTE_REPORT` | 是否编译/启用 HTTP 上报 |
| `...REMOTE_DEVICE_ID` | 匿名设备 ID |
| `...REMOTE_HTTP_ENDPOINT` | HTTP 接收端地址 |
| `...REMOTE_HTTP_TOKEN` | 可选 Bearer Token；不得提交真实值 |
| `...REMOTE_QUEUE_DEPTH` | RAM 队列深度 |
| `...REMOTE_HTTP_TIMEOUT_MS` | HTTP 连接/收发非活动超时 |
| `...REMOTE_RETRY_MAX` | 首次发送后的最大重试次数 |
| `...REMOTE_RETRY_INITIAL_MS` / `...MAX_DELAY_MS` | 指数退避参数 |
| `...REMOTE_THREAD_STACKSIZE` / `...THREAD_PRIORITY` | 工作线程资源与优先级 |

密钥类配置不应被打印。启动日志只记录协议、主机是否已配置、队列深度和 TLS 是否启用。

### 5.5 HTTP 首版实施内容

首版只实现 HTTP，先完整验证“本地告警不依赖网络”的边界；不同时接入 MQTT。已新增以下三个固件核心文件：

| 文件 | 职责 |
| --- | --- |
| `app/audio_event/reporter/event_reporter.h` | 定义上报事件结构、`init/deinit/enqueue` 接口和可观测统计接口。 |
| `app/audio_event/reporter/event_reporter.c` | 固定长度事件队列、mutex/semaphore、独立上报线程、重试/退避、成功/失败/丢弃计数。 |
| `app/audio_event/reporter/event_reporter_http.c` | HTTP `POST` 后端：构造 JSON、连接、发送、读取响应并判定 `2xx` 成功。 |

事件队列应保存值对象而非 `event_name` 指针，避免入队后调用方的内存或类别配置变化影响待发送数据：

```c
struct report_event_s
{
  uint32_t sequence;
  uint64_t monotonic_ms;
  int event_id;
  uint16_t confidence_permille;
  char event_name[16];
};
```

| 文件 | 修改内容 |

### 5.6 启用与部署步骤

1. 使用 `ccf_audioevent/board/esp32s3-devkit/configs/audio_event_8class_remote_http` 构建联网联调固件。该 profile 以 8-class 音频基线为基础，合入 ESP32-S3 Wi-Fi station、IPv4 TCP/UDP、DNS、DHCP renewal、`wapi` 和 HTTP reporter；为释放 Wi-Fi 所需的内部 DRAM，它将 196608 B TFLM arena 一次性分配到 PSRAM。网络项参考 `nuttx/boards/xtensa/esp32s3/esp32s3-devkit/configs/wifi/defconfig`，而非直接覆盖音频 profile：

   ```sh
   ./build.sh ccf_audioevent/board/esp32s3-devkit/configs/audio_event_8class_remote_http menuconfig
   ./build.sh ccf_audioevent/board/esp32s3-devkit/configs/audio_event_8class_remote_http -j8
   ```
2. 在本地 `menuconfig` 配置匿名设备 ID、可信局域网 HTTP endpoint 和有界队列/超时参数。profile 只启用 `EXAMPLES_AUDIO_EVENT_REMOTE_REPORT`，端点与 Token 均保持空值，不能将现场 endpoint、SSID、密码或 Token 提交回仓库。
3. 在上位机运行：

   ```sh
   python3 scripts/remote_receiver.py --host 0.0.0.0 --port 8080
   ```

4. 将 endpoint 设置为例如 `http://192.168.1.10:8080/api/v1/audio-events`。接收端地址应替换为上位机在同一可信局域网中的实际 IP。

5. 首次启动先运行 `audio_event --model-smoke`。日志必须显示
   `[model] arena PSRAM ptr=0x3c... size=196608`，而不是 `arena static
   DRAM`；随后回放已知 WAV 并重新记录端到端推理耗时。该 profile 不替代
   内部 DRAM arena 的正式 ESP-NN 性能基线。

### 5.7 串口 WAPI 配网（STA）

完成烧录并进入 NSH 后，使用 `wlan0` 作为 station 接口。以下示例适用于
WPA2-PSK/CCMP；SSID 和密码仅在串口会话中输入：

```sh
nsh> ifup wlan0
nsh> wapi psk wlan0 <wifi_password> 3
nsh> wapi essid wlan0 <wifi_ssid> 1
nsh> renew wlan0
nsh> ifconfig wlan0
nsh> ping <receiver_ip>
```

其中 `3` 表示 `WPA_ALG_CCMP`，缺省 WPA 版本为 WPA2。WPA3-SAE 可使用
`wapi psk wlan0 <wifi_password> 3 3`。`renew wlan0` 成功后才具有 DHCP 分配的
IPv4 地址；`ifconfig` 与 `ping` 成功是启动 `audio_event` 前的联网判据。

`wapi save_config wlan0` 会把当前凭据保存到板端配置存储。首轮联调不执行该
命令，避免凭据持久化和后续清理问题；如确有自动重连需求，应将其作为单独的
凭据存储与擦除方案评审，而不是提交到 defconfig。

当前后端仅支持明文 `http://` 用于受控局域网演示；TLS、证书校验、MQTT、Flash 持久化队列和手机推送均不在首版范围内。

HTTP 稳定后若需 MQTT，再新增 `reporter/event_reporter_mqtt.c` 并实现与 HTTP 相同的内部发送接口；队列、线程和事件数据契约不应重复实现。

## 6. 上位机和手机端最小实现

### 6.1 HTTP 接收端

最小上位机接收端应提供：

- `POST /api/v1/audio-events` 接收并校验 JSON；
- 按 `event_id` 去重，写入日志或轻量数据库；
- 返回明确的 `2xx`、`4xx`、`5xx`；
- 一个网页列表显示时间、设备、事件、置信度和上报状态。

现场演示可在同一局域网笔记本运行接收端，手机浏览器访问该网页。接收端不可用时，不影响设备本地告警。

### 6.2 MQTT 接收端

可使用局域网 broker 和订阅程序/网页网关展示 `audio_event/<device_id>/events`。应记录 QoS、是否 retain、去重规则和离线状态主题。事件消息默认不使用 retain，避免新订阅者把历史事件误当成刚发生的告警。

## 7. 测试与验收

### 7.1 功能测试

| 用例 | 预期结果 |
| --- | --- |
| 正常网络 + 本地事件 | 本地告警立即出现；服务端收到一条正确 JSON |
| 连续多个事件 | 顺序上报或以 `event_id` 可追溯；不丢/不重复到未说明程度 |
| 服务器返回 500/超时 | 本地告警不延迟；工作线程有限退避重试 |
| Wi-Fi 断开后恢复 | 本地检测连续可用；网络恢复后队列按策略发送 |
| DNS/认证失败 | 显示可定位错误；无高频死循环、无崩溃 |
| 队列满 | 明确统计丢弃或覆盖；采集与推理不中断 |
| 设备重启 | 本地功能正常恢复；按首版 RAM 队列边界记录未发事件行为 |

### 7.2 性能与稳定性测试

- 对比启用/关闭上报时的事件识别成功率、端到端本地告警延迟、模型耗时、RAM 和 30 分钟连续运行结果。
- 网络异常期间重点检查采集线程是否持续接收 PCM、模型是否持续推理、队列内存是否有上界。
- 记录 Wi-Fi 初始化、IP 获取、连接状态、队列高水位、成功数、失败数、重试数和丢弃数；日志中不得输出密钥。

### 7.3 完成定义

- [x] 网络 I/O 位于独立任务；事件入队不执行 DNS、连接或 socket I/O。
- [x] 队列、超时和重试均有上界，并有可观测统计。
- [ ] 完成断网恢复、服务端错误、队列满、连续运行等固定测试并保留日志。

## 8. 风险与应对

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 网络请求在主循环执行 | 音频丢帧、延迟和崩溃 | 仅允许工作线程处理网络 I/O |
| 断网无限重试 | CPU/内存被耗尽 | 有界队列、超时、有限重试和指数退避 |
| 事件重试导致重复通知 | 手机告警风暴 | `event_id` + 服务端幂等去重 |
| Wi-Fi/TLS 资源不足 | 连接失败或压缩音频资源 | 先完成 HTTP/MQTT 明文 LAN 原型，再评估 TLS 内存与证书 |
| 硬编码凭据 | 凭据泄露 | 配置注入、日志脱敏、提交前扫描 |
| Flash 队列频繁写入 | Flash 寿命与复杂度风险 | 首版 RAM 队列，明确重启丢失边界 |
| 上位机不可用 | 远程演示中断 | 本地告警为主；接收端可独立重启和验证 |

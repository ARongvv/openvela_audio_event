# 多模型协同推理实施方案

> 状态：实施设计，尚未创建双模型调度代码或新增模型资产。
> 目标：在保持当前 `audio_event` 低延迟、持续采集和本地告警能力的前提下，支持串行级联、并行双模型与影子评估三种多模型运行方式。
> 适用基线：ESP32-S3、16 kHz 单声道 PCM16、1 秒窗口、250 ms hop、当前 4-class INT8 DS-CNN。

## 1. 当前基础与结论

当前性能 profile 已采用 ESP-NN 加速三个 Conv2D、两个 DepthwiseConv2D 和空间 Mean。文件回放实测：

| 指标 | 当前实测值 | 含义 |
| --- | ---: | --- |
| 特征提取 `feature` | 60–70 ms | 49 × 40 × 3 log-mel/delta 特征 |
| 模型阶段 `infer` | 20 ms | 输入量化、TFLM Invoke、输出反量化 |
| 单窗口 `total` | 80–90 ms | 含日志与事件判决，不含等待下一 hop |
| hop | 250 ms | 每个新窗口的目标更新周期 |
| 处理余量 | 约 160 ms | `250 - 90`，当前无积压 |

因此，当前 DS-CNN 适合作为**常驻快速模型**。但不应因为还有约 160 ms 余量，就在主线程中无条件再串行执行一个大模型：第二模型的特征、推理、串口输出和偶发 cache/PSRAM 抖动都会侵蚀余量。多模型方案的首要目标是“结果不过期、采集不中断”，其次才是提高分类能力。

当前已有的数据流为：

```text
I2S / WAV 文件
  -> capture_thread_main()：512-sample block、2 秒 PCM ring、能量门控
  -> 主线程：复制最新 1 秒 PCM 窗口
  -> feature_extract_compute()：49 x 40 x 3
  -> event_classifier_predict()：4-class DS-CNN
  -> event_detector_update() -> alert / UI / remote reporter
```

采集线程与主线程已经分离，但当前默认并非 SMP 固核；详情见
[ESP32-S3 双核采集与推理流水线方案](ESP32-S3双核采集与推理流水线方案.md)。以下方案不能让同一个
TFLM `MicroInterpreter::Invoke()` 自动双核化，也不能允许多个线程并发访问同一解释器。

## 2. 三种运行模式

| 模式 | 执行关系 | 适用目标 | 优点 | 主要代价 | 推荐度 |
| --- | --- | --- | --- | --- | --- |
| A. 串行级联 | 快模型先判定，命中候选才提交精模型 | 降低误报、扩展关键词/细分类 | 大模型低频运行，功耗和平均延迟低 | 前级漏检会使后级不运行 | 首选 |
| B. 并行双模型 | 同一 PCM 窗口分别交给两个独立模型 | 两个模型互补、需要实时融合 | 不依赖前级门限，召回更高 | 需要 SMP、更多 RAM、共享资源竞争 | 条件采用 |
| C. 影子模型 | 主模型告警，副模型只记录结果 | 新模型上线前的安全评估 | 不影响现有告警口径 | 仍有额外算力和 RAM 开销 | 每次换模型必做 |

建议实施顺序是 **C → A → B**：先证明副模型正确、资源可控，再把它接入正式判决；只有确认两个模型必须每个 hop 都运行时，才做并行双模型。

## 3. 模式 A：串行级联（推荐首版）

### 3.1 目标结构

```text
PCM ring（2 s，持续写入）
  -> P0 能量门（已有）
  -> M1 快速 DS-CNN：每个有效 250 ms hop，约 20 ms
  -> candidate gate：P(class) / 连续帧 / 事件类型
  -> 单槽 secondary queue（仅保留最新 PCM 快照或 feature 快照）
  -> M2 精模型：关键词 KWS、细分类 DS-CNN、BCResNet 等
  -> fusion：确认、否决、标签细分
  -> 现有 detector / alert / UI / reporter
```

`M1` 负责“是否值得进一步计算”，`M2` 负责“是什么、是否确认”。可选例子：

| M1 候选条件 | M2 工作 | 最终动作 |
| --- | --- | --- |
| `cough` 概率超过候选阈值 | 咳嗽/非咳嗽二分类或更大事件模型 | 确认后再远程上报 |
| `speech` 概率超过阈值 | KWS / WakeNet / 自训关键词模型 | 关键词命中后告警 |
| `knock` 概率超过阈值 | 节奏/次数确认模型 | 防止偶发冲击误报 |
| `background/silence` | 不运行 M2 | 直接结束当前 hop |

前级门控必须依据指定类别概率与连续帧规则，不能只使用 argmax。例如可配置为
`P(cough) >= candidate_threshold` 连续两帧才提交 M2；阈值必须由冻结校准集决定。

### 3.2 调度规则

1. 采集线程只写入 PCM ring、更新样本计数和能量门控，**不执行模型**。
2. 主线程仍每个 hop 复制最新 1 秒窗口并执行 M1；M1 的结果可立即走原有 `event_detector`。
3. 命中候选时，向 M2 投递带 `timestamp_ms` 的任务。队列深度固定为 1：新任务覆盖尚未处理的旧任务。
4. M2 完成后，只有当结果时间戳仍在可接受的新鲜度范围内才融合；过期结果仅记录统计，不触发告警。
5. M2 慢于候选到达速率时增加 `secondary_overwrite_count`，不能建立无界队列，也不能阻塞采集或 M1。

队列内容依模型输入决定：

| M2 输入 | 建议投递内容 | 原因 |
| --- | --- | --- |
| 与 M1 相同的 49 × 40 × 3 特征 | immutable feature slot | 避免重复 FFT/log-mel；必须有独立 slot，不能复用正在写的 `g_features` |
| 不同特征形状但仍为音频模型 | PCM 窗口副本 + 时间戳 | M2 在自己的线程/上下文生成特征 |
| KWS 流式模型 | PCM 片段、pre-roll 起点、连续帧序号 | 避免丢失关键词首字，支持按帧送入 |

当前 `g_audio_window`、`g_features` 和 `g_probabilities` 都是全局单缓冲，只适用于主线程串行处理。多模型任务不得直接保留这些指针；应改为明确拥有的 slot 或复制。

### 3.3 何时适合直接同步串行

只有满足下式时，才可在主线程同步运行 M2：

```text
feature_M1 + infer_M1 + feature_M2 + infer_M2 + P95(其他开销) < 250 ms
```

并且应保留至少 20% 余量。当前 M1 `total` 约 90 ms，若 M2 仅偶发、且 P95 不超过约 100 ms，可以先进行同步 POC；正式版本仍建议采用单槽 worker，以隔离偶发尖峰。对于目前 reference BCResNet1 约 1.19 s 的 Invoke，绝不能同步串行；它只能作为低频异步确认模型，或先压缩/专项加速。

## 4. 模式 B：并行双模型

### 4.1 目标结构

```text
CPU0（建议）                         CPU1（建议）
-------------------------------     ---------------------------------
I2S DMA / capture_thread_main()     主线程：PCM snapshot + M1
PCM ring / energy gate              M2 worker：feature + Invoke
                                    fusion / detector / alert

              只传递带序号的 immutable PCM/feature slot
```

并行是“两个独立模型同时计算”，不是“一个模型拆到两个核”。需要先启用
`CONFIG_SMP=y`、`CONFIG_SMP_NCPUS=2`，再在应用中可选地绑定采集线程至 CPU0、主线程/M2
worker 至 CPU1。亲和性接口和风险见[双核流水线方案](ESP32-S3双核采集与推理流水线方案.md)。

同一核上并行创建两个 worker 并不会提高吞吐，反而会带来时间片切换、PSRAM/cache 竞争和不可复现的
P95。因此在未完成 SMP 验证前，模式 B 实际上应退化为“交替调度”或模式 C，不得宣称并行加速。

### 4.2 并行模型契约

每个模型必须拥有以下资源，不能共享可变对象：

```text
模型字节数组、MicroMutableOpResolver、MicroInterpreter、tensor arena、
input/output tensor 指针、量化参数、输出概率数组、profile 计数器
```

可共享的只包括只读模型元数据、只读特征 slot（发布后不可修改）和 PCM ring 的快照结果。若两个模型的特征规范完全一致，推荐“主线程提取一次特征 → 发布 feature slot → 两模型读”；若不一致，宁可各自从 PCM snapshot 提取，也不能错误复用不同的 log-mel/量化规范。

### 4.3 融合策略

首版只采用可解释的规则融合，不先引入黑盒学习融合：

| 规则 | 说明 |
| --- | --- |
| confirm | M1 和 M2 都达到各自门限才告警，降低误报 |
| override | M2 的高置信特定类别覆盖 M1 的粗类别 |
| fallback | M2 超时/失败时保留 M1 本地告警，并标记 `secondary=unavailable` |
| disagreement log | 两模型类别不同仅记录 `disagree_count`，用于离线校准，不立即改变阈值 |

融合需限制等待：M1 结果到达后最多等待 `FUSION_WAIT_MS`（初期建议不大于一个 hop）；超时必须有明确的
M1-only 或不告警策略。最终策略取决于任务偏好：安全优先时允许 M1-only 先本地提醒、M2 仅影响远程上报；误报优先时等待 M2 确认。

## 5. 模式 C：影子模型与安全上线

影子模式是新模型的默认上线方式：M1 仍使用当前已验证的 detector/alert；M2 使用相同窗口或候选窗口运行，但只打印/保存：

```text
[secondary] t=... model=bcresnet class=... confidence=... latency=...
[fusion-shadow] primary=... secondary=... agree=0/1 age=... ms
```

至少覆盖固定 WAV、不同 SNR、不同距离、真实麦克风三类输入，并统计：

- M2 初始化成功率、arena 使用量、任务覆盖次数和 P95；
- 与 M1 一致/不一致的混淆表；
- 原有 knock/cough 的误报、漏报和端到端延迟是否回归；
- 长时间运行的 heap、线程栈、水位和 `secondary_overwrite_count`。

只有影子数据和冻结回归集证明 M2 有实际价值，才将融合结果接入告警。

### 6.1 建议的公共数据结构

```c
struct model_result_s
{
  uint64_t timestamp_ms;
  uint32_t sequence;
  uint32_t latency_ms;
  int class_id;
  float confidence;
  bool valid;
};

struct secondary_job_s
{
  uint64_t timestamp_ms;
  uint32_t sequence;
  enum secondary_input_kind_e input_kind;
  /* 一个独占 PCM 或 feature slot；发布后只读。 */
};
```

`sequence` 用于拒绝旧结果：如果 M2 返回时 `sequence < last_fused_sequence`，该结果不可倒灌到较新的
M1 分类中。slot 的释放必须由 scheduler 统一完成，不能由生产者和消费者各自猜测。

## 7. Kconfig 与 profile 设计

建议的新增配置如下，名称在实施前需经 Kconfig 依赖检查确认：

| 配置 | 建议默认值 | 用途 |
| --- | --- | --- |
| `EXAMPLES_AUDIO_EVENT_MULTI_MODEL` | `n` | 多模型总开关；关闭时保持当前单模型二进制行为 |
| `EXAMPLES_AUDIO_EVENT_MULTI_MODEL_MODE` | `SHADOW` | `SHADOW`、`SERIAL_CASCADE`、`PARALLEL_DUAL` 三选一 |
| `EXAMPLES_AUDIO_EVENT_SECONDARY_MODEL` | 具体模型选择 | 例如 TFLM KWS、细分类 DS-CNN、BCResNet |
| `EXAMPLES_AUDIO_EVENT_SECONDARY_ARENA_SIZE` | 按预检结果填写 | 次模型独立 tensor arena，禁止与主模型共用 |
| `EXAMPLES_AUDIO_EVENT_SECONDARY_QUEUE_DEPTH` | `1` | 固定推荐为 1；大于 1 须给出不过期证明 |
| `EXAMPLES_AUDIO_EVENT_SECONDARY_MAX_AGE_MS` | `500` | 过期次模型结果不参与融合 |
| `EXAMPLES_AUDIO_EVENT_CANDIDATE_THRESHOLD` | 校准值 | M1 投递 M2 的概率门限 |
| `EXAMPLES_AUDIO_EVENT_FUSION_WAIT_MS` | 校准值 | 等待 M2 的最大时长 |
| `EXAMPLES_AUDIO_EVENT_CPU_AFFINITY` | `n` | 仅 `SMP` 下可见的线程亲和性开关 |
| `EXAMPLES_AUDIO_EVENT_MULTI_MODEL_PROFILE` | `n` | 输出 M1/M2/queue/fusion 分项统计，不能默认打开 |

建议新增而非修改已有 profile：

```text
audio_event_espnn_profile                 当前单模型正式性能基线
audio_event_secondary_shadow              新模型只观察、不影响告警
audio_event_serial_cascade                M1 候选触发 M2
audio_event_parallel_dual_smp             SMP + affinity 的双模型实验
audio_event_parallel_dual_verify          双模型数值/输出/资源验证，非性能口径
```

每个 profile 必须保存对应 `.config`、模型 SHA-256、arena 使用量和 ESP-NN 开关。不要在
`audio_event_espnn_profile` 上直接叠加试验性次模型，否则会失去当前 80–90 ms 的可复现基线。

## 8. 分阶段实施计划

| 阶段 | 实施内容 | 主要文件 | 完成条件 |
| --- | --- | --- | --- |
| M0：规格冻结 | 确定 M2 的类别、特征、量化、输入窗口、模型 SHA、是否需要 pre-roll | `docs/`、模型资产 | 有桌面黄金向量和 arena 预估 |
| M1：独立预检 | 在 `tflm_benchmark` 或专用 smoke 程序测 M2 的算子、arena、CCOUNT、输出 hash | `model/*`、benchmark profile | M2 可单独初始化和稳定 Invoke |
| M2：影子单线程 | 加 secondary backend 与 scheduler，但只记录，不改变告警 | `model/secondary_*`、`pipeline/*` | 主模型回归无变化；M2 的输出/延迟可记录 |
| M3：串行级联 | 候选门控、单槽覆盖、融合 fallback | `fusion/*`、`detector/*`、Kconfig | 没有队列积压；确认逻辑符合冻结用例 |
| M4：SMP 并行 POC | 启用 SMP、亲和性、双 worker、slot 生命周期与锁检查 | board defconfig、`main/*`、scheduler | 10 分钟采集稳定；P95 与单核对比完整 |
| M5：正式化 | 阈值校准、回归、日志归档、功耗与鲁棒性报告 | docs/logs/configs | 达到性能、误报/漏报、稳定性验收线 |

M2 完成前禁止改变线上告警决策；M4 不应在 M3 未证明需要每 hop 双模型时开始。

## 9. 性能、内存与并发验收

### 9.1 性能口径

分别记录，不混用：

| 字段 | 含义 |
| --- | --- |
| `feature_primary_ms` / `infer_primary_ms` | M1 分项耗时 |
| `queue_wait_secondary_ms` | M2 从提交到开始的等待；持续增大即表示积压 |
| `feature_secondary_ms` / `infer_secondary_ms` | M2 分项耗时 |
| `fusion_wait_ms` | 为等待次模型而增加的延迟 |
| `result_age_ms` | M2 结果相对当前音频窗口的年龄 |
| `secondary_overwrite_count` | 因最新优先策略而丢弃的旧任务数 |
| `total_ms` | 主链路对每个 hop 的实际处理时间 |

正式实时性条件：`total` 的 P95 小于 250 ms，且实时设备模式下 `wall` 不持续落后于音频时间。对于异步 M2，
还要求 `result_age_ms` P95 小于业务允许的告警时延；“采集没有停止”不能替代“结果仍然新鲜”。

### 9.2 内存与线程规则

- 主/次模型使用独立 arena；测量 `arena_used` 和静态缓冲峰值后再决定是否放入 PSRAM。
- 每个 worker 的栈大小通过实际 stack watermark 验证；不以 benchmark 任务栈替代应用 worker 栈。
- PCM ring 仍由短锁保护；在锁外执行特征、Invoke、融合、OLED、HTTP。
- 一次只允许一个线程调用某个 interpreter；若使用 M2 worker，主线程不得调用 M2 的 `predict()`。
- 串口 TRACE/VERIFY 仅用于数值验证，不计入正式性能数据。

## 10. 测试矩阵

| 场景 | 输入 | 必测结果 |
| --- | --- | --- |
| 单模型回归 | 当前 `combined_A_pure.wav` | 类别、告警、`feature/infer/total` 与现有基线一致 |
| 候选命中 | knock/cough/speech/关键词冻结音频 | M2 仅在预期条件下投递；pre-roll 完整 |
| 候选未命中 | silence/background/纯噪声 | M2 调用率低；无错误告警 |
| 双模型不一致 | 专门构造/收集样本 | `disagree_count`、融合规则、fallback 符合定义 |
| 队列压力 | 高频候选、M2 人为延迟 | 队列保持深度 1、旧任务覆盖、采集无中断 |
| 实时采集 | `/dev/audio/pcm_in1` 连续至少 10 分钟 | 无 read/DMA 错误、无重启、P95 与结果新鲜度达标 |
| 资源压力 | 最大 arena + UI + 可选网络上报 | 无 AllocateTensors 失败、堆/栈无持续增长 |
| 鲁棒性 | 不同 SNR、距离、噪声、扬声器回放 | 与单模型的误报/漏报、延迟和功耗对比 |

## 11. 风险与取舍

| 风险 | 后果 | 处理原则 |
| --- | --- | --- |
| M1 门限过高 | M2 从未运行，产生前级漏报 | 用召回优先的候选阈值与校准集确定门限 |
| M1 门限过低 | M2 调用过多，功耗与延迟失控 | 统计调用率；引入连续帧、能量门控和冷却 |
| M2 比 hop 慢 | 结果过期、队列积压 | 深度 1、最新覆盖、年龄丢弃；不能排队“补算” |
| 两模型共享 interpreter/缓冲 | 数据竞争、崩溃、随机输出 | 每模型独立 runtime；slot 发布后只读 |
| SMP/cache/PSRAM 竞争 | P95 比单核更差 | 先测单核影子，再测 SMP 未绑定/绑定；按 P95 决策 |
| 模型标签不一致 | 融合错误告警 | 冻结类别映射、模型 SHA 与输出维度检查 |
| 把影子数据当正式精度 | 指标不可解释 | 影子仅比较；正式误报/漏报以带真值的冻结集统计 |

## 12. 推荐的首个落地目标

最小且风险可控的下一步不是直接并行 BCResNet，而是：

1. 将一个输入/输出契约明确、可独立运行的次模型接入 **影子模式**；
2. 复用当前 2 秒 PCM ring，以单槽 PCM snapshot 投递，记录 M2 延迟、结果年龄、覆盖次数和 arena；
3. 在 `combined_A_pure.wav`、真实麦克风与噪声集上确认主模型的 `total` 仍满足 250 ms；
4. 若 M2 确实只需在候选事件出现时工作，再启用串行级联；
5. 只有业务要求 M1/M2 每个 hop 都有结果、且资源/实时性测量支持时，才实施 SMP 并行双模型。

这一路径既保留当前 ESP-NN 单模型的可靠性能基线，也为关键词、细分类、BCResNet 或远程告警前确认模型留下可控的扩展接口。

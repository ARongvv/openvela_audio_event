# ESP32-S3 音频特征提取优化方案

## 1. 目标与当前结论

本文针对当前 4-class `ds_cnn_small` 模型的音频前端，规划在 **不改变训练/部署特征契约** 的前提下，降低
ESP32-S3 上 `feature_extract_compute()` 的耗时。该前端将 16 kHz 单声道 PCM 转换为
`[49, 40, 3]` 的 float 特征：log-Mel、delta、delta-delta。

已验证的五卷积 + Mean ESP-NN backend 已使纯模型 `Invoke()` mean 降至 17.591 ms。真实 WAV 播放的
`audio_event --profile --no-oled` 日志中，特征提取约为 60--70 ms、模型阶段约为 30--40 ms、
整窗处理约为 100--110 ms。因此系统已低于 250 ms hop，但特征提取已成为当前最大的单项 CPU 开销。

本方案的首要目标不是修改模型或降低采样率，而是：

1. 得到 FFT、Mel、对数和 delta 的可解释 CCOUNT 基线；
2. 在 float 特征逐元素一致（优先 bit-exact）的条件下消除重复计算；
3. 在真实 WAV 与实时采集上验证类别、概率、触发结果和实时性不回退。

模型推理的 ESP-NN 选择、节点验证和性能口径见
[Reference 与 ESP-NN 性能对比操作手册](../项目基线/Reference与ESP-NN性能对比操作手册.md)。本文只处理其上游的
PCM→特征链路。

## 2. 当前实现与耗时来源

实现位于 [feature_extract.c](../../app/audio_event/dsp/feature_extract.c)，固定参数位于
[audio_event_config.h](../../app/audio_event/audio_event_config.h)：

| 项目 | 当前值 | 含义 |
| --- | ---: | --- |
| PCM 采样率 | 16,000 Hz | 单声道 PCM16 |
| 分析窗口 | 480 samples / 30 ms | Hann 窗 |
| 帧移 | 320 samples / 20 ms | 每个模型窗口 49 帧 |
| FFT | 512 点实数 KissFFT | 每帧补零 32 samples |
| Mel band | 40 | 125--7,500 Hz 的三角滤波器 |
| 输出 | `49 × 40 × 3 = 5,880` float | log-Mel、一次 delta、二次 delta |
| 推理 hop | 250 ms | 每次处理一段 1 秒 PCM 窗口 |

每次调用当前都会重新处理完整 1 秒 PCM：

```text
16,000 PCM samples
  → 49 次「PCM→float + Hann + 512 点实数 FFT」
  → 49 × 40 次 Mel 能量计算
  → 1,960 次 log/scale/clamp
  → 1,960 次一次 delta + 1,960 次二次 delta
  → [49, 40, 3] float features
```

其中当前 Mel 实现对每个 frame 的每个 band 都扫描 FFT 的 256 个非 DC bin；一次窗口约有
`49 × 40 × 256 = 501,760` 次 bin 范围判断。命中的 bin 会重复计算幅值 `sqrtf(real² + imag²)`，
并重复计算三角滤波器权重。Hann 窗、bin 的 Mel 坐标和 Mel band 边界已在初始化时预计算，但权重、
幅值和跨窗口结果尚未复用。

`event_classifier_predict()` 内的 5,880 元素 float→int8 量化属于 `infer` 计时边界，不属于本文所说的
`feature=60--70 ms`；可单独优化，但不能把它记作特征提取收益。

## 3. 优化原则与禁止项

### 3.1 必须保持的特征契约

当前模型依赖下列语义，第一、二阶段不得改变：

- 16 kHz PCM16 输入、30 ms 周期 Hann 窗、20 ms 帧移、512 点 FFT；
- 跳过 DC bin、125--7,500 Hz、40 个三角 Mel band；
- 对**幅值**而不是功率谱做 Mel 加权；
- `logf(mel_energy + 1e-6)`、offset/scale/clamp 和 delta 边界复制规则；
- 特征元素顺序 `[frame][band][channel]`。

特别禁止把 `sqrtf` 直接删除并改成能量平方、用不同 Mel 公式、缩短模型窗口或减少 band 后仍复用原模型。
它们都会改变输入分布；除非同步重训/重新量化并完成精度评估，否则不是“性能优化”。

### 3.2 统一验收条件

每次代码修改都必须同时通过：

1. **特征回归**：对固定 PCM/WAV 产生 5,880 个旧/新 float 特征，记录最大绝对误差、最大相对误差和
   不同元素数；第一阶段目标为逐元素 bit-exact。
2. **模型回归**：对相同特征和 WAV，比对 int8 输入、输出概率、top-1 类别、事件触发时间和次数。
3. **性能回归**：同一 ESP32-S3、240 MHz、同一固件条件，记录 warmup 后至少 100 个实际 Invoke 窗口的
   feature P50/mean/P95；不使用串口 TRACE/VERIFY 的耗时作为正式性能。
4. **实时性回归**：`feature + infer` P95 小于 250 ms，持续文件回放和实时采集均无积压、重启或音频错误。

## 4. 分阶段实施

### 阶段 0：用 CCOUNT 划分前端子阶段

**目的**：先确认计算热点，避免在非热点上做复杂改动。

在 `feature_extract_compute()` 中仅为 profiling profile 增加 CCOUNT 采样，分别累计：

| 字段 | 计时范围 |
| --- | --- |
| `window_cycles` | PCM16→float、Hann 相乘、padding |
| `fft_cycles` | `kiss_fftr()` |
| `magnitude_mel_cycles` | 幅值计算、Mel 加权累加 |
| `log_cycles` | `logf`、scale、clamp |
| `delta_cycles` | 两轮 delta |

计时读取本身有少量开销，因此应按整次窗口累计，并通过独立 Kconfig/profile 控制；常规
`audio_event_espnn_profile` 不应默认打开。现有毫秒级 `[profile] feature=...` 保留作为端到端口径，
CCOUNT 用于决定优化顺序。

涉及文件：

- `app/audio_event/dsp/feature_extract.c`；
- `app/audio_event/main/audio_event_main.c`（输出聚合结果）；
- `app/audio_event/Kconfig` 和新的专用 defconfig（若需要开关）。

### 阶段 1：稀疏 Mel 权重与幅值复用

**目的**：不改变算法，只移除当前重复的判断、除法和 `sqrtf`。

初始化时为每个 band 计算并保存：有效 `first_bin`/`last_bin`、按 bin 升序排列的三角权重。每一帧 FFT
完成后，先遍历 bin 1--256 一次，生成幅值缓存；再按各 band 的有效 bin 范围进行乘加。

```text
当前：每个 band 扫描全部 256 bin，命中时即时求 weight 和 magnitude
优化：每帧先算 256 个 magnitude；每个 band 只遍历有效 bin，读取预计算 weight
```

实现必须保持每个 band 的 bin 升序累加顺序，避免仅因浮点加法顺序改变造成可避免的舍入差异。预计算权重时
使用与现有代码一致的 float 公式；若仍出现差异，先定位并记录原因，不得直接放宽验收门槛。

预期：该阶段不会减少 49 次 FFT 或 1,960 次 `logf`，但应显著减少 Mel 内层循环的无效判断、浮点除法和
重复幅值计算。具体收益以阶段 0 的 `magnitude_mel_cycles` 为准，不能预先把理论减少量写成实测结论。

涉及文件：

- `app/audio_event/dsp/feature_extract.c`；
- 新增 host/板端特征回归工具或测试向量；
- 对应测试日志与本文件的结果表。

### 阶段 2：验证编译优化与直接 int8 输出

先通过实际编译命令确认 `feature_extract.c` 使用的优化级别。TFLM 使用 `-O3` 不代表 C 前端也使用相同级别；
若前端不是速度优先的优化级别，可只对该源文件试验 `-O3`，并同时观察 Flash 增长、数值回归与真实耗时。

随后可让 DSP 根据模型 input 的 scale/zero-point 直接生成 int8 特征，调用
`event_classifier_predict_quantized()`。该改动主要减少当前 `infer` 内的 5,880 次 `lround` 和逐元素写入，
不应被记录为 `feature` 优化。它同样必须与旧 float→int8 的结果逐元素一致。

涉及文件：

- `app/audio_event/Makefile`（仅在确认需要时加入局部编译选项）；
- `app/audio_event/dsp/feature_extract.c/.h`；
- `app/audio_event/main/audio_event_main.c`；
- `app/audio_event/model/event_classifier.cc`（复用已有量化入口，不修改模型）。

### 阶段 3：流式 log-Mel 环形缓存

当前 hop 为 250 ms，而模型帧移为 20 ms；250 ms 不是 20 ms 的整数倍。因此不能只缓存前一窗口的
49 个 20 ms 帧：下一个窗口会交替到相差 10 ms 的帧相位。直接复用会改变特征时间位置，属于错误优化。

保持 250 ms hop 的正确方案是以全局 **10 ms** 时间网格持续计算 log-Mel，并维护环形缓存：

```text
PCM 捕获线程
  → 每 10 ms 产生一个 30 ms log-Mel frame
  → 写入 log-Mel 环形缓存

每 250 ms 推理任务
  → 根据窗口起点选择同一相位的 49 个 frame
  → 计算 delta / delta-delta
  → 写入模型输入并调用 ESP-NN 推理
```

稳态每 250 ms 只新增 25 个 10 ms frame，而不是在 `process_window()` 中突发重算 49 个 frame；这会降低
FFT/Mel 平均工作量并削平处理峰值。需要为启动填充、文件 EOF、环形缓存覆盖、采集/推理并发和 timestamp
一致性设计明确状态机。

另一种选择是将 hop 调整为 240 ms（12 个 20 ms frame），即可使用 20 ms 网格并每次只生成 12 个新 frame；
但它改变检测频率和事件时间戳，必须作为产品行为变更单独评估，不能与纯性能优化混在同一提交中。

涉及文件：

- `app/audio_event/main/audio_event_main.c`（采集、窗口调度和任务同步）；
- `app/audio_event/dsp/feature_extract.c/.h`（单帧 API、缓存与 delta API）；
- `app/audio_event/audio_event_config.h`（缓存容量和时间网格常量）；
- `app/audio_event/Kconfig`、测试数据和实时回归脚本。

### 阶段 4：替换数值内核（独立研究项）

只有阶段 1--3 的收益不足时，才评估 ESP32-S3 专用 FFT、固定点 FFT 或 `logf` 近似。这些方案可能减少
CPU 周期，却大概率改变特征浮点值；需要冻结新前端、重新生成训练/验证特征、重新量化并报告准确率、误报/漏报
和鲁棒性变化。ESP-NN 不覆盖 FFT/Mel/log 运算，不能把它当作这一步的替代。

## 5. 推荐实施顺序与提交边界

| 提交 | 内容 | 是否改变特征数值 | 通过条件 |
| --- | --- | --- | --- |
| 1 | 阶段 0：CCOUNT 子阶段观测与日志格式 | 否 | 可重复输出分项 cycle；关闭开关时无性能影响 |
| 2 | 阶段 1：稀疏 Mel 权重、幅值缓存、特征回归 | 否，目标 bit-exact | 特征/模型/WAV 回归通过，记录 P50/mean/P95 |
| 3 | 阶段 2：局部编译优化或直接 int8 路径 | 否，目标量化结果一致 | 记录 Flash、`feature` 与 `infer` 的独立收益 |
| 4 | 阶段 3：流式缓存 | 否，输出窗口应等价 | 文件与实时长稳回归通过，无积压 |
| 5 | 阶段 4：新数值内核 | 可能 | 重训/重新量化和完整精度评估通过 |

每个提交只包含一个可回归的阶段；在 commit message、原始日志和性能表中同时记录模型 SHA-256、ESP-NN
节点选择、CPU 频率、hop、输入 WAV、供电/串口条件和固件 revision。

## 6. 基准记录模板

在性能日志中新增或填写如下表，而非只记录一次 `feature` 整数毫秒：

| revision/profile | 输入 | 窗口数 | feature P50/mean/P95 | FFT mean | Mel mean | log mean | delta mean | infer P50/mean/P95 | total P95 | 数值回归 |
| --- | --- | ---: | --- | --- | --- | --- | --- | --- | --- | --- |
| baseline | `combined_A_pure.wav` | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 基准 |

对照音频至少包括静音、背景、knock、cough，以及当前
[`combined_A_pure.wav`](../../test_data/combined_A_pure.wav)。对于实时麦克风，还应记录削波、静音插入、
底噪和周期性失真；否则“特征更快”可能只是输入质量退化造成的假象。

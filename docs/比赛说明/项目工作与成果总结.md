# 音频事件检测比赛：项目工作与成果总结

本文为后续比赛报告、答辩和演示准备而写，汇总 `ccf_audioevent` 已完成的实际工作、可量化结果和可复现证据。
所有“已完成”均指已有源码、配置、真机日志或模型产物支撑的事项；方案、预检和候选模型单独标记，不能写成
已经部署的能力。

## 1. 项目一句话概述

项目在 ESP32-S3 + openvela/NuttX 上实现了离线音频事件检测闭环：

```text
I2S 麦克风 / 板端 WAV
  → PCM 窗口与能量门
  → log-Mel + delta + delta-delta 特征
  → INT8 TFLite Micro + ESP-NN
  → knock / cough / background / silence 分类、事件判定与告警
```

重点增量不是仅运行一个模型，而是将 Espressif ESP-NN 作为 ESP32-S3 的 TFLite Micro backend 接入
openvela，并经过 reference 对照、逐字节验证、CCOUNT 测量和真实 WAV 回放验证，使当前模型的纯推理
mean 从 346.271 ms 降至 30.948 ms。

## 2. 已完成的核心工作

### 2.1 模型训练、量化与筛选

模型训练工作区共训练和评估 **38 个候选模型**，覆盖：

- DS-CNN 的 small/medium/large、数据清洗、类别扩展、GLU、Dilation、SE 等实验；
- 针对 ESP-NN 通道约束设计的 DS-CNN-S3 系列；
- BC-ResNet、TC-ResNet 与关键词识别模型；
- float 与 INT8 TFLite 的量化误差、FAR、MISS 与模型大小比较。

当前板端部署的是 4-class `small_clean` INT8 DS-CNN：模型大小 **11,984 B**、参数约 2K，离线 INT8
评估约 **93.2%**。训练汇总还得到了两个有价值的后续候选：

| 候选 | 离线 INT8 指标 | 模型大小 | 当前状态 |
| --- | ---: | ---: | --- |
| `s3_small_4class` | 约 96.0% | 约 12 KB | 面向 ESP-NN 的候选，尚未替换板端部署模型 |
| `large_clean` | 约 97.2% | 约 30 KB | 精度优先候选，尚未完成板端实时性验证 |
| `bcresnet1_8class` | 约 94.2% | 约 126 KB | 已完成 TFLM 预检，尚不适合直接部署 |

可报告的结论是：完成了多架构、量化和数据清洗对比，并选择小型 INT8 DS-CNN 作为当前可在板端实时运行的
基线；不能把候选模型的离线精度写成当前设备端准确率。

### 2.2 ESP32-S3/openvela 音频检测闭环

实现并接入了下列端侧组件：

- 16 kHz I2S/INMP441 采集与单声道 PCM16 转换；
- WAV 文件回放，支持与实时麦克风共用同一处理路径；
- 1 秒滑动窗口、`[49, 40, 3]` log-Mel + delta 特征提取；
- TFLite Micro INT8 模型加载、量化输入、概率输出和事件检测器；
- knock、cough、background、silence 四分类及阈值、连续命中、冷却策略；
- 串口告警、OLED/LVGL UI 接口、可选异步 HTTP 上报；
- RMS/峰值能量门：静音/低能量窗口可跳过 DSP 和推理。

这满足赛题的“采集→预处理/特征提取→模型识别→输出/告警”的本地离线闭环要求。主链路及模块位置见
[目录架构说明](../目录架构说明.md)。

### 2.3 ESP-NN 移植与受控加速

为 ESP32-S3 接入了 ESP-NN，而没有错误地在 Xtensa LX7 上使用 ARM CMSIS-NN/CMSIS-DSP 或 HiFi backend。
实际工程工作包括：

- 固定 ESP-NN 上游源码、许可证说明及本地建链脚本；
- openvela `apps/mlearning/tflite-micro` 的 Kconfig、CMake/Make 源码集成；
- TFLM `Conv2D` 与 `DepthwiseConv2D` wrapper，保留量化、padding、activation、per-channel 参数；
- filter 对齐副本和 Tensor Arena scratch，避免未对齐权重或动态分配造成的不稳定；
- 按 output tensor ID 选择节点的单选/位掩码配置；
- TRACE/VERIFY：先用 reference 逐字节比较，出现差异时恢复 reference 输出；
- 独立 reference、单节点、组合验证、组合性能 profile，以及 CCOUNT benchmark。

因此加速路径是“按节点、按模型、可验证地启用”，而不是一次性把全部算子替换后只观察是否能运行。具体实现和
复现步骤见 [ESP-NN 移植实施指南](../优化文档/ESP-NN移植到openvela实施指南.md)。

### 2.4 公平性能测量与数值一致性验证

在同一 ESP32-S3、240 MHz、确定性非零 INT8 `pattern`、warmup=20、repeat=100 的条件下，使用 CCOUNT
测量 `MicroInterpreter::Invoke()`，结果如下：

| 配置 | ESP-NN 节点 | mean 时延 | P95 时延 | Arena 实际使用 | output hash | 相对 reference |
| --- | --- | ---: | ---: | ---: | --- | ---: |
| 全 reference | 无 | 346.271 ms | 346.299 ms | 22,788 B | `0x77a10bab` | 1.0000× |
| 三 Conv2D | 23、25、27 | 82.809 ms | 82.825 ms | 32,324 B | `0x77a10bab` | 4.1815× |
| 三 Conv2D + DW24 + DW26 | 23、24、25、26、27 | **30.948 ms** | **30.973 ms** | 44,324 B | `0x77a10bab` | **11.1887×** |

结论：当前五卷积节点组合在保持 output hash 一致的前提下，纯模型推理时延降低 **91.062%**。性能结果不是
单次串口计时：reference 与 ESP-NN 均完成 100 次记录，并保留 P50、mean、P95 和 max。完整口径与全部组合
结果见 [Reference 与 ESP-NN 性能对比操作手册](../项目基线/Reference与ESP-NN性能对比操作手册.md)。

### 2.5 真实音频、资源镜像和端到端验证

为 ESP32-S3 N16R8 上半区规划了 `0x800000–0xFFFFFF` 的 **8 MiB LittleFS** 资源区，并提供 WAV 镜像生成、
独立烧录和 `/data` 挂载验证流程。项目已将约 5 MiB 的 `combined_A_pure.wav` 写入资源镜像，并在 NSH 确认
`/data/combined_A_pure.wav` 可读取。

使用五节点 ESP-NN 的 `audio_event` 性能 profile 回放该 WAV 时，观测到：

| 端到端指标 | 观测值 | 说明 |
| --- | --- | --- |
| 特征提取 `feature` | 约 60--70 ms | 当前最大单项 CPU 开销 |
| 模型阶段 `infer` | 约 30--40 ms | 含应用侧量化、Invoke 与反量化 |
| 单窗口总时间 `total` | 约 100--110 ms | 低于 250 ms hop |
| File A 运行结果 | `status=0` | 已保存原始 picocom 日志 |
| 能量门 | 539 次实际推理、110 次跳过 | 该次 File A 回放观测值，非功耗测量 |

这说明 ESP-NN 的纯模型收益在真实特征、文件输入和应用调度链路中仍能落地，且当前处理时间没有超过
250 ms hop。原始日志索引见 [logs/readme.md](../../logs/readme.md)，端到端复现实验见
[audio_event 与 ESP-NN 端到端对比](../项目基线/audio_event与ESP-NN端到端对比.md)。

### 2.6 工程化、文档与可复现性

项目不是只保留一次成功日志，而是提供：

- 多套板级 defconfig：reference、verify、三 Conv、DW24、DW26、五节点组合、端到端 profile；
- ESP-NN 本地建链、LittleFS 镜像生成、资源烧录和模型导入脚本；
- `tflm_benchmark`：独立 Invoke CCOUNT、算子 CSV 和 BCResNet 预检；
- WAV 测试文件、JSON 事件时间线、picocom 原始日志及命名索引；
- ESP-NN 复刻手册、性能对比手册、优化方案、目录架构说明和异常排查材料；
- `LICENSE`、`NOTICE` 和第三方依赖材料，便于审查 ESP-NN 来源与许可。

这些材料直接服务于比赛的可复现、工程化和开源合规要求。

## 4. 报告中应明确的边界

以下事项有价值，但当前不能写成“已经完成的交付”：

- **特征前端优化**：已完成瓶颈分析和实施方案，尚未完成稀疏 Mel、流式缓存或固定点 FFT 的性能提交。
- **`s3_small_4class` / `large_clean`**：离线候选指标优于当前模型，尚未完成模型替换后的真机节点 trace、数值验证和实时性测试。
- **BCResNet 8-class**：已能在 TFLM benchmark 中预检，但 reference 推理约 1.19 s，不适合作为当前实时部署模型。
- **双核流水线、远程上报、关键词识别、鲁棒性专项**：已有方案或基础代码，需以相应真机日志和指标完成后再作为复赛成果计分。
- **低功耗**：能量门降低了无效 DSP/TFLM 次数，但没有进行电流、电量或续航测量，不能报告具体功耗下降百分比。

这类边界写清楚会让报告更可信：已完成成果可直接展示，后续工作可作为清晰的复赛路线。

## 5. 可直接用于报告的成果表述

> 本项目完成了基于 openvela/NuttX 与 ESP32-S3 的本地音频事件检测闭环，实现 I2S/WAV 输入、
> `[49,40,3]` log-Mel 特征、INT8 TFLite Micro 分类、事件判定与本地告警。针对 ESP32-S3 Xtensa LX7，
> 项目将 ESP-NN 以受控 TFLM backend 方式接入，并对 3 个 Conv2D 和 2 个 DepthwiseConv2D 完成数值验证。
> 在相同 240 MHz 硬件、固定输入、100 次 CCOUNT 测试中，模型 mean Invoke 时延由 346.271 ms 降至
> 30.948 ms，实现 11.1887× 加速且输出 hash 一致。真实 5 MiB WAV 回放中，应用端推理约 30--40 ms、
> 总窗口处理约 100--110 ms，满足 250 ms hop 的实时处理约束。项目同时提供板级 profile、资源镜像、
> 原始串口日志和复现文档，支持审查和复测。

引用这段前，应在附件中放入本文件第 2.4 节的性能表、`logs/测试日志/` 原始日志、构建命令和演示视频，
以便评审快速核验。
